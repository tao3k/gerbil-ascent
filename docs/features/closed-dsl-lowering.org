* Cause and design

The failing consumer request spent its original 9.677-second remaining budget
inside =open_sources=, loading dynamic macro phases. A native sampler attributed
832 of 833 samples to dynamic loading; later file observations showed forward
progress through SDK generation files. These observations establish expensive
cold phase loading, not a permanent lock deadlock. Link-preserving resources,
SDK-path controls and loader-flag controls alone still timed out.

=interface/closed-source.ss= recognizes a complete, closed source shape before
constructing any declaration. It then calls the existing POO relation, term,
clause, rule and Program/Fragment constructors. Composition, preparation,
source admission, execution, result ownership and publication remain in their
existing modules. Unrecognized syntax uses the original upstream macro path.
Construction or execution errors never trigger a second lowering attempt.

This follows Gerbil's =compiler/optimize-call.ss:89-129=: establish calling shape
and binding conditions before applying a specialization. It also follows the
explicit syntax dispatch in =compiler/optimize-xform.ss:16-40=. It is a bounded
specialization of an existing language, not a general Scheme evaluator.

* Recognition obligations

- Relations have empty initial rows and explicit canonical scalar predicates.
- Terms are variables, wildcards or scalar literals; positive and negative
  atoms and multiple heads keep their original constructor order.
- Guards use declared variables and a fixed set of canonical primitives.
  =and=/=or= retain Scheme values and short-circuit errors. The existing engine
  still requires the final guard result to be boolean.
- Guard inputs cannot shadow operator/syntax bindings. A single native syntax
  factory generates fixed arities 0–32 and the matching recognition bound.
  Wider guards and unknown expressions select the original macro path.
- Macros, includes, callbacks, initial facts, storage extensions and explicit
  bounds select the macro path before any constructors run.
- The existing bounded reader and the full declaration/source checks remain
  authoritative. Guards are not promoted into checked projection operators.

* Verification layers

The complete immutable zero-argument =define-evidence= inventory has a matching
closed scope. Admission stores constructor closures, never previously created
Evidence values. Every invocation calls the original declaration/value
constructors anew. Duplicate constructors, unknown explicit exports, helpers,
parameters, explicit explanation callbacks and foreign imports select the
original module path before declaration construction. The existing trust,
reader and scope-charge checks still precede either route.

=ClosedEvidenceScope.qnt= models whole-scope selection, fresh invocation and
unchanged scope charging, with partial-selection, cached-instance and rejected
publication mutations. The Lean scope model records constructor equivalence
and distinct invocation identities under an explicit freshness assumption.
Native original-macro tests supply the implementation correspondence; neither
formal model proves arbitrary Scheme semantics or the parser implementation.

=ClosedDslLowering.lean= proves closure compilation equivalent to direct
expression interpretation under the same primitive bindings, including error
propagation and Scheme truth for scalar zero. It is a mathematical expression
model, not an extracted proof of the Scheme parser or runtime.

=ClosedDslLowering.qnt= checks whole-source selection, one construction attempt
and private failure. Partial selection, retry and rejected-owner mutations
produce counterexamples. Native tests separately compare identical datums with
a forced original macro expansion, including fixed/incorrect guard arity,
short-circuit errors, recursion and wider-guard fallback. Python tests exercise
the ordinary native SourceSession lifecycle and admission contracts.
