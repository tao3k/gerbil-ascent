* Purpose and boundary
:PROPERTIES:
:CUSTOM_ID: scheme-dsl-overview
:END:

This is the short overview for discussing the next Scheme relational
language.  [[file:research/scheme-dsl/language-history.org][Language history]] explains how the ideas developed;
[[file:research/scheme-dsl/index.org][the research index]] links individual paper readings with PDF locators.
The [[file:research/agent-inference/index.org][Agent inference research index]] studies the deployment-time interface.
The current implementation has selected Rust Ascent 0.8.0 behavior and a
Scheme/POO program model.  That oracle constrains matching results, not
our future Scheme spelling or abstraction boundary.

One small relational form remains legible:

#+begin_src scheme
((path source target) <-- (edge source target))
((path source target) <-- (path source middle) (edge middle target))
#+end_src

The arrow derives facts.  Body atoms state joins and equality of repeated
logic variables.  Scheme functions can build program values around these
rules; admitted functions can compute local values inside rules.  These
are different language phases and need different guarantees.

* Design feel: a small relational core within Scheme
:PROPERTIES:
:CUSTOM_ID: scheme-dsl-design-feel
:END:

The public authoring surface should read as Scheme composition of
relational programs, with a small visible rule core.  It should not
recreate Rust's =if=, =let=, =for=, and =if let= body tokens as a second
Scheme control language.  Program fragments are ordinary values that
Scheme functions can parameterize and combine.  Their relation handles,
imports, exports, and rules become an inspectable logical program before
execution.  A rule-time function has declared binding modes, effects,
and dependencies; it cannot be an opaque call disguised as a relation.

#+NAME: scheme-design-shape
| Surface | Proposed role | Semantics visible to admission |
|---------+---------------+--------------------------------|
| Scheme function | Constructs or specializes fragment values | Resulting fragment and public signature |
| Rule arrow and atoms | Derivation, joins, logic-variable equality | Binding modes and dependency edges |
| Term expression | Row-local scalar computation | Explicit bound inputs and output term |
| Pointwise relation adapter | Zero, one, or many output rows per fixed input tuple | Input/output modes and declared stability contract |
| Negation, aggregation, lattice join | Explicit nonpositive or ordered operations | Strata, order/join laws, finite-height obligations |
| Solve and query | Complete one admitted snapshot, then read it | Completion/failure status and immutable result |

=relation-view= is one provisional adapter for row-local functions, not
the entire higher-order language.  Arbitrary Scheme closures are not
proved pure, total, stable, or monotone by accepting =procedure?=.

* Agent-facing Library is a first-class design case
:PROPERTIES:
:CUSTOM_ID: scheme-agent-library
:END:

The internal rule core and the external Agent interface are both
Library requirements.  Deployment-time inference is the main use:
an Agent may search for current evidence, propose candidate
facts/rules/queries, inspect diagnostics, execute a bounded program,
ask why or why-not, and revise.  Search is one input path, not the
definition of all reasoning.  Nonrelational arithmetic, code, planning
or hypothesis checks need their own semantics behind a shared attempt
and feedback envelope.  The Library returns observations for the
model's next turn; it does not change the model's trained weights or
learned reward model.  A search hit is not an unverified fact insertion
into the fixed point.

#+NAME: scheme-agent-loop
| Agent action | Library response | Required boundary |
|--------------+------------------+-------------------|
| Propose a fact or rule | Inspectable candidate with syntax/schema/mode diagnostics | No source authority or MRR admission |
| Execute a query | Complete rows or explicit partial/failure under exact program, snapshot and limits | No completed-answer claim on budget failure |
| Ask why or why-not | Rule/source witness or bounded missing-premise explanation with status | One witness is not complete provenance |
| Search and revise | New attempt against named source generation | Search hit remains a candidate until source binding |

The first executable case is a graph/search transcript containing a
correct recursive rule, an undeclared helper relation, and a wrong
recursive join that compiles.  The Library must diagnose the first,
distinguish full outputs for the latter, and return a grounded why or
why-not result before the Agent retries.  See the
[[file:research/agent-inference/index.org::#agent-inference-gate][research gate]].  The present evaluator returns rows and candidate
supports in limited paths; a general Agent proposal/diagnosis and
provenance API is *not yet implemented*.  MRR remains the later
semantic admission owner, while POO Flow owns Agent context and
effect handoff.

* Current design choices for discussion
:PROPERTIES:
:CUSTOM_ID: scheme-dsl-decisions
:END:

The table makes our present direction explicit.  "Working choice" means
a proposal awaiting the listed discriminator, not an implemented API.

#+NAME: scheme-design-decisions
| Decision | Working choice | Reason | Discriminator before commitment |
|----------+----------------+--------+---------------------------------|
| Core rule | Keep arrow, relation atoms, repeated-variable equality | Preserves an analyzable join graph and recursive meaning | Complete facts and plan visibility against pinned oracle |
| Host syntax | Replace Rust-shaped body control forms in one direct migration | Scheme already supplies functions and lexical composition | One fixture spanning scalar, filter, pattern, generator, recursion |
| Higher-order construction | Scheme functions return first-class fragment/program values | Reuse the host language without executing at construction | Two parameterized instantiations with private relations |
| Private names | Fresh relation handles per fragment instantiation; explicit shared imports/exports | Avoid accidental capture through equal printed symbols | Compose two instances with same private label |
| Public contract | Export relation shapes and handles; keep internal graph for admission | Permit refactoring private rules while retaining planner evidence | Interface and combined-program diagnostics |
| Rule-time calls | Only declared pointwise adapters or later checked operators | Hidden relation reads and mutable captures break planning | Reject unbound mode, mutation, hidden dependency, divergence |
| Recursion domain | Require finite-height evidence for closure claim; otherwise bounded failure is explicit | Finite output per call does not imply finite closure | Infinite successor fails; finite successor completes |
| Nonpositive operations | Negation and general aggregation read completed lower strata | Combined fragments can introduce negative cycles | Late-composition cycle rejection |
| Lattice state | Explicit order and join contract, separate from set relations | A user join needs law and height evidence | Finite-model law checks and closure comparison |
| Lifecycle | Construct/inject, admit, solve, query as distinct stages | Late composition and source replacement change answers | Negation-sensitive late composition and repeated query |
| Source withdrawal | Recompute the accepted snapshot until deletion semantics are proved | Increasing-delta theory does not justify deletion | Failure-atomic replacement with full output comparison |
| Higher-order delta | First specialize fragments to inspectable IR; research typed operator changes later | Datafun S20's proof concerns a typed calculus | Naive versus transformed full-result equivalence and scale |

The intended order is: establish the integrated semantics and admission
boundary; directly migrate the Scheme surface after qualification; then
research a restricted higher-order operator IR.  This does not require
copying Flix types or Ascent's Rust grammar into Gerbil.

* Semantic and lifecycle sketch
:PROPERTIES:
:CUSTOM_ID: scheme-dsl-architecture
:END:

A conceptual program flow is below.  Names and syntax are explanatory,
not promised API spelling.

#+begin_src scheme
;; Schematic, not implemented.
(def (reachability edge-handle)
  (with-private-relations ((path (vertex vertex)))
    (fragment (import edge-handle) (export path)
      ((path x y) <-- (edge-handle x y))
      ((path x z) <-- (path x y) (edge-handle y z)))))
(def reach (reachability edge-handle))
(def program (compose (inject edge-handle edge-rows) reach))
(def checked (admit program))
(def solved (solve checked))
(query solved (exported-relation reach 'path))
#+end_src

Construction can use normal Scheme functions and POO declarations.
Admission validates the assembled program: relation identity and arity,
lexical captures, bound inputs, dependencies, negative cycles, and
operator effects.  Fixed-point execution uses visible positive atoms
for join and delta planning.  Solving produces either a completed
snapshot or explicit failure; querying does not rerun a program.

#+NAME: scheme-language-layers
| Phase | Object | Obligation |
|-------+--------+------------|
| Construct | Fragment/program values | Fresh private handles; explicit imports/exports |
| Admit | Immutable logical IR | Modes, schema, effects, dependency graph, strata |
| Evaluate | Sets and ordered state | Stable monotone contribution; closure or failure |
| Session | Accepted source snapshot | Replacement invalidation and failure atomicity |
| Query | Solved immutable result | Repeatable projection without mutation |

A fixed point may call a pointwise function =f : I -> finite-set(O)=.
For a growing input relation =R= it contributes the union of =f(i)=
for =i in R=.  This contribution grows with =R= only when =f= remains
stable for that snapshot and reads no hidden changing relations.
Even then, a recursive successor can generate unbounded facts.  A
fact budget is an explicit failure bound, never evidence of completed
least-fixed-point termination.  A finite-domain claim requires domain
checks and rejection of out-of-domain rows.

* Acceptance and open questions
:PROPERTIES:
:CUSTOM_ID: scheme-dsl-migration
:END:

The first integrated fixture should combine fragment reuse with private
handles, source injection/replacement, scalar projection, zero/one/many
row adapters, recursion, lattice refinement, negation, explicit solve,
and repeated queries.  Compare complete facts with an independent
finite model and pinned Rust cases where their semantics overlap.
Inspect admitted dependency edges, selected indexes and delta positions;
exercise admission failures, failure atomicity, and matched scale.
Only then should a replacement surface remove the old Rust-shaped
Scheme forms and update callers and examples together.

#+NAME: scheme-discussion-questions
| Question for us | Why it changes the design | Next evidence |
|-----------------+---------------------------+---------------|
| Should private relation handles be first-class values or exist only in a fragment scope? | Controls hygiene and how fragments share relations | Two-instantiation and cross-module fixture |
| Should the pointwise adapter be one =relation-view= declaration or several typed operators? | Controls ergonomics and planner precision | Compare integrated fixture and diagnostic quality |
| Which restricted Scheme expressions can be mechanically certified pure and stable? | Sets the boundary between trusted and verified rule-time code | Scope, capture, effect, and divergence counterexamples |
| Which finite domains and lattice orders can be admitted without hidden truncation? | Determines when completion can be claimed | Independent finite fixed-point model |
| What is the smallest public program signature that supports safe composition? | Balances abstraction against combined-program admission | Late cycle and schema-change fixtures |
| When is typed higher-order delta worth the compiler cost? | Controls the transition beyond first-order specialization | Reference evaluator, transformed evaluator, scale profile |

These are design questions, not deferred proof by terminology.  A
restricted operator IR may eventually support checked monotonicity and
higher-order change semantics.  Until then, rule-time arbitrary Scheme
procedures are trusted adapters with bounded claims.
