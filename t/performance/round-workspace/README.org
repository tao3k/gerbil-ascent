#+title: Complete native round workspace qualification

* Ownership and source study

The full evaluator is frozen at =cf706aee296a1d11ca2824c045a65f27dca3c7c7=.
Only relative imports are relocated. Both engines share unchanged dependencies,
the same installed Gerbil =1cfb032= and the same compiled native library root.

Gerbil =src/gerbil/compiler/optimize-base.ss:334-340= creates a private method
table only when needed. =src/std/list/list-builder.ss:5-24= expresses an
owner-controlled collection through hygienic syntax. ASCENT applies these
patterns to an explicit retained frontier and an invocation-owned write set:
rows, row admission, callbacks and physical indexes remain with the engine.
Gerbil =src/std/struct/lru.ss:45-67= binds typed record projections directly
with =using=; the workspace uses the same expression form. The private records
are final; their factories own all mutable containers. The eligibility boundary
also omits view-injection and lattice staging vectors from native Set/hash
rounds. Single-relation engines retain direct traversal.

Canonical Set/hash lanes use sparse delta reset and commit selection. A reset
visits the retained nonempty frontier and nonempty totals of the new stratum.
A commit visits the union of the preceding frontier and actual admitted writes,
in ascending declaration order. Only after the whole commit succeeds does the
write set become the next frontier. Empty unchanged lanes keep their native
version-owned index entry. Custom providers, views and lattice joins preserve
the existing complete traversal and version behavior. Source appends register
new frontier members; a partial timeout retains its already committed frontier.

* Gates fixed before timing

Each scenario consumes the complete engine and all published sizes/rows.
Declarations and immutable analysis are prepared outside warm clocks; every
measured leg constructs its engine and executes through complete publication.
Cold includes declaration construction. Independent expected closure membership
is checked in every leg; sorted rows only normalize enumeration for comparison.

|----------+-------------------+----------|

Every scenario has 20 alternating process CPU (user+system) pairs with natural
GC, 20 separate ASP consumer admissions and five alternating VM allocation
pairs. Allocation alone collects before each leg; negative counters reject.
Allocation must be <=110% baseline +8192 bytes. ASP p95 must be <=999ms.
The entire six-scenario run has one fixed 90-second bound. No environment
selector, Python harness, subprocess scheduler or upstream source build is used.
