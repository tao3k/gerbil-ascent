* Candidate admission and lowering

** Repeated schema resolution: candidate/program.ss:129,256

=candidate-inspect= builds source and combined alist schemas. =atom-check= uses
=assq= for every head/body/query atom. Facts independently search the source
schema, and heads independently search derived declarations. Worst-case schema
lookup work is proportional to atom/fact references times relation declarations.
A source/derived/all schema frame could resolve names once per inspection while
keeping distinct write authority and arity checks. Arity zero is a valid value;
absence must have an explicit representation.

The admitted schema cannot be retained blindly across mutable snapshots.
Duplicate-relation diagnostics precede fact and rule diagnostics; head admission
precedes body binding diagnostics. Keep those order contracts.

** Variable scope grows with occurrences: candidate/program.ss:146,193-253

Positive body atoms cons every logical-variable occurrence into =bound=, including
already-bound variables. =memq= then scans that occurrence list for negation,
operators, freshness and head admission. The relevant size is variable occurrences,
not distinct bindings. For Q membership reads and B accumulated occurrences,
worst-case scope work is O(Q*B). Repeated uses can enlarge B without extending
the logical scope.

A private rule-local symbol set should own membership and binding extension.
Positive atoms bind; negation/operators only read; computation/reduction bind
fresh output names. Wildcard, duplicate-binding and first located diagnostic
behavior must remain exact. No arbitrary function or candidate callback runs
at this inert inspection stage.

** Facts are repartitioned for every source: candidate/program.ss:353-367

For each source declaration, =candidate-program= filters the complete candidate
fact list, maps matching rows, then appends them to original source rows. With
R sources and F candidate facts, relation-name selection performs R*F checks,
plus temporary filtered lists. At R=64/F=128 that is 8192 name comparisons
(the count is derived from loop structure, not a timed measurement).

Partition admitted facts once in original order. Preserve source rows before
candidate rows, duplicate occurrences and candidate labels in all evidence.
Lowered inputs containing candidate facts do not confer source authority. The
public POO relation/rule/program construction contracts remain the consumer.

* Candidate evidence construction

** Whole-edge BFS scans: candidate/reasoning.ss:233-264

=candidate-graph-walk= visits each reachable vertex once, but its inner loop scans
all records each time. Work is O(V_reachable*E), even when each vertex has one
outgoing edge. Support paths share tails; path copying is not the principal
issue in this chain case. The search must continue after finding the target
because it also returns the complete reachable cut.

A Scheme audit probe extracts this current private algorithm and adds one counter
at each record visit. It verifies shortest support length and independent chain
reachability before accepting the count. It runs without Python or a new harness.
The receipt is ignored =.cache/ascent/large-flow-audit/graph-scan.log=:

| Vertices | Edges | Observed record probes |
|----------+-------+------------------------|
| 32 | 31 | 992 |
| 64 | 63 | 4032 |
| 128 | 127 | 16256 |
| 256 | 255 | 65280 |

An invocation-owned ordered adjacency index can reduce record selection to one
construction pass plus reached out-edges. Its allocation cost and small/empty
controls still require A/B qualification. Preserve shortest nonempty support,
source-first ties, hypothetical edge labels, repeated source occurrences and
reachable-cut order. In particular origin=target does not automatically prove
a nonempty path. Temporal horizon-frontier semantics differ from this support/
cut protocol; their walkers must not be merged merely because both use BFS.

** Receipt stages and repeated trust boundaries: candidate/reasoning.ss:343-567

=reasoning-attempt= interleaves inspection, native admission, solve, query,
evidence and optional positive/absence/stratified proof production in one deep
control tree. Failure classification depends on its stage. These stages warrant
named result records and explicit publication policy, coordinated with candidate
schema/scope/fact preparation rather than separate cosmetic rewrites.

Receipt verifiers recheck mutable snapshot content binding and reinspect candidate
data. Proof producers/verifiers have their own current-snapshot checks. These are
real public trust boundaries, not automatically removable duplicate work.
An internal owned admission context might amortize preparation within one call;
measure its construction/copy cost and preserve budget charging. Do not cache
validation across calls or let one producer's proof stand in for independent
verification. Current source/proposal/certificate mutation controls stay mandatory.

* Retained engine execution and update ownership

=program/evaluate.ss:91-981= binds schema, all/delta rows, versions, index owners,
storage owners, lattice state and counters inside one construction closure.
Nested owners cover =commit-view!=, staged Set flush, row emission, body execution,
retained fixed point, result publication and source append/replacement/recovery.
=program/initialization.ss= already names initialization buffers; use that existing
ownership pattern rather than introduce a second generic engine framework.

=append-source!= at lines 799-904 also chooses update policy. For negation,
aggregation, lattice interaction or a previously replayed engine, it copies source
rows, rebuilds source declarations, constructs an engine and runs it before
publishing the append. Repeated updates can therefore pay repeated whole solves.
Positive Set appends already use a buffered persistent log and batch admission.

The eager path preserves immediate errors and atomic publication. Simply delaying
it to =run!= would change failure timing and accepted state. Work should separate
update preparation, candidate execution and publication, with explicit state and
recovery ownership. Bulk behavior requires a defined transaction contract and a
matched workload; a module move alone cannot claim CPU improvement. Native row
loops should borrow their state once, rather than pay record access/dispatch per
field just to shorten the coordinator.

* Typed compilation and public declarations

=program/higher-order.ss:296-486= combines type freezing, scoped term validation,
finite-domain collection and beta/fixed-point lowering. Term copies are reused
only after children, lexical scope and rebuilt signatures are checked. This can
repeat rebuilding for shared descriptors, but early memoization keyed only by node
identity would skip scope checks. Every visit is also budgeted. The type snapshotter
already checks/charges before reuse; retain that contract. A measured next design
would separate scoped validation from owned representation reuse while preserving
all budget boundaries and escaped-parameter rejection.

=program/objects.ss:426-468= scans prior exports for duplicate detection and scans
all declarations per source handle. These are real construction costs, but their
frequency and contribution to a full admitted program are unmeasured. Its clause
planning already uses POO generic dispatch and bounded/lazy symbol indexes.
Keep that public extension axis. A large scope should not be represented by a
new fixed arbitrary cutoff without evidence about scope lifetime and read reuse.

=program/syntax.ss= uses =defsyntax=/=defrules= for major grammar forms. File size
alone does not justify rewriting macro dispatch or claiming runtime gains.
Expansion cost needs an expansion workload, not a runtime-only solve benchmark.
