* Study: compose persistent source logs without copying unchanged bases

Installed Gerbil =2591dcd=, =compiler/optimize-top.ss:1269-1281=, returns
the existing expression when there are no lifted bindings to wrap.
=runtime/util.ss:268-283= implements =foldl= with a list cursor and one
accumulator. These two examples guide this change: reuse admitted immutable
data when there is nothing to compose, and carry the comparison cursor as
the fold state. Gerbil's =andmap2= truncates to the shorter list; it is not
an exact ordered-list equality operation.

Previously the session snapshot, evaluator source lookup and update selection
each reconstructed =(append base (reverse additions))=. Even an unchanged
source copied every base header; equality allocated that list solely to compare
it. =program/source-log.ss= now owns both operations. Empty additions return
the admitted persistent base. Nonempty composition still creates new list
headers in source order, preserving row identity. Comparison folds over the
base with the remaining candidate suffix or =#f= as its only state, then
compares reversed additions after a successful prefix. Order, duplicate
multiplicity, missing rows and excess rows retain their previous semantics.

This relies on the existing admission contract: captured source bases,
addition spines and rows are read-only. Session snapshots own their vector
headers; sharing an unchanged base does not authorize mutation. Nonempty
composition retains detached headers. Session, evaluator and update selection
use the common owner; =build.ss= adds only that production module.

or nullable types. The transferable lesson is to distinguish qualification from
the actual transform. It does not implement ASCENT update transactions.

* Feature: bounded dependency traversal and source membership in retained updates

The installed compiler's =optimize-top.ss:703= (=extract-keyword-args=)
uses an explicit remaining suffix and accumulator in a named tail loop.
Its lesson here is to make progress and ownership visible in traversal state;
it is not a dependency invalidation algorithm. The installed runtime's
=hash.ss:385-387,574-575= gives ordinary hash tables an =equal?= test and
implements =hash-get= through their reference method. These source contracts
permit a structurally equal source membership lookup without changing row
representation or introducing unchecked compiler declarations.

Native retained-update selection previously rescanned every compiled rule
until no additional relation became affected. Reverse-ordered dependency
chains require one new full scan per level. Selection now constructs local
body-to-head adjacency once, seeds a pending list from changed sources, and
marks a relation before pushing it. Each relation is visited at most once;
duplicate edges and recursive cycles cannot reenqueue an already marked
relation. Positive atoms, negation and aggregates preserve their dependency
roles, including every head of a multi-head rule. Work is bounded by relation
count plus the constructed dependency edges, independent of source rule
order. Eligibility checks, immutable analysis layout, rule activation order,
and the fallback for opaque callbacks/providers are unchanged. No new cache
or build interface is introduced.

source list for each distinct retained row, producing quadratic membership
work when an unchanged relation had many source rows. Set source admission
already owns an =equal?= membership table; reuse now consults that table before
replacing it with the completed closure's fresh membership. Relations with user
field checks retain the original linear equality walk, because a callback may

* Study: native synchronization at the cache owner

Gerbil =2591dcd= supplies the synchronization boundary in the table itself:

| Upstream source | Concrete boundary |
|-----------------+-------------------|
| =runtime/hash.ss:261-271= | Locked primitive methods acquire and release their Locker with =dynamic-wind= |
| =runtime/hash.ss:276-285= | Reference and insertion use the respective read/write operations |
| =runtime/hash.ss:385-407= | =make-hash-table= wraps the table when =lock:= is supplied |
| =runtime/hash.ss:434-458= | Weak Gambit tables retain the same locking wrapper |
| =runtime/hash.ss:491-492= | =make-hash-table-eq= forwards constructor options and fixes identity equality |
| =compiler/base.ss:392-402= | Snapshot the current executor under its mutex, close it outside that mutex, and clean up publication afterward |

The transferable rule is to put synchronization at the owner of the shared
state, with explicit boundaries around work that may reenter the system.
ASCENT's =program/scheme-checked.ss= already uses native locking for its weak
stable-procedure table. The analysis, schema and positive-plan caches now follow
the same native table convention.

Previously, =program/analysis= and =core/positive-plan= each implemented a
manual =dynamic-wind= wrapper around primitive table lookups and insertions.
Analysis and schema shared one mutex even though no operation atomically
accessed both tables. Each of the three caches now constructs its own weak,
identity-keyed table with a named native mutex. The two wrappers and their
separate global lock bindings are removed.

Lookup, version validation, cold construction and insertion retain their
original order. Declaration inspection, schema callbacks and rule compilation
stay outside primitive-operation locks. In particular, a caller-supplied
analysis builder may inspect or build another analysis. A failed build cannot
replace the prior cached entry. Native hash operations retain dynamic cleanup;
there is no new manually managed lock lifetime.

The change does not turn lookup/build/insert into an atomic transaction or a

** Production change and ownership

Previously =program/actor-session.ss= mixed source validation/copying, name

** Official sources and application-specific inference

[[https://gerbil.scheme.org/guide/intro.html][Gerbil's actor introduction]] describes an actor as a thread reacting to messages.
[[https://gerbil.scheme.org/reference/std/misc/threads#on-all-processors][Gerbil's thread utilities]] state that multiple OS-thread runtime support must
be enabled to use multiple cores, and show =##current-vm-processor-count=.
The historical documented =on-all-processors= module path is absent in the
installed 0.19 tree; the VM primitive itself is present and tested.

[[https://raw.githubusercontent.com/gambit/gambit/master/doc/gambit.txi][Gambit's thread fairness specification]] describes scheduling runnable
threads, blocking, priority and quantum expiry. Its memory-coherency section
requires application synchronization around concurrent mutable writes.
[[https://mailman.iro.umontreal.ca/pipermail/gambit-list/2020-March/009357.html][Marc Feeley's scheduler explanation (2020)]] distinguishes VM processors from
Scheme threads and describes SMP work stealing between runnable-thread queues.
Its 2020 stability comparison is historical and not a claim about this SDK.

For our CPU-intensive component closures, selecting the active VM processor
count is an application choice informed by those sources. It is not a
universal actor-count rule: blocking I/O actors can outnumber processors.
The runtime schedules Scheme threads. Our round owner admits dependency-ready
components, replenishes work after terminal messages and serializes merges.
Each compute worker has at most one 32-row batch awaiting credit; checkpoint
messages bound cancellation observations. These credits are application
backpressure, not replacements for Gambit's scheduler or its thread quantum.
No additional priority/affinity policy or manually inserted yields is added.

* Prepared queries: retain export selection and apply the current solution

LeanPoo =247d1d6094b6af1bb873f69564b271bc978730ed= separates selecting
factories from applying them to a context. Its preparation-cache,
context-cache, borrowed-view and observed-view examples make the lifetime
of preparation distinct from the lifetime of observed data. The native
consumer now implements that distinction directly in =scheme-query.ss=.

=relational-prepare-query= resolves one fragment export once and returns a
read function. =relational-prepare-queries= resolves an ordered checklist,
including repeated labels, into a read function. Preparation does not read
rows or construct an engine. Each application validates the supplied solution
and its completion before observing rows, then selects that result's reader.
An empty checklist still requires completion and observes no relations.

#+begin_src scheme
(def read-view (relational-prepare-queries fragment '(reach edge reach)))
(def first (relational-session-run session))
(def first-view (read-view first))
(def next
  (relational-session-replace-sources! session fragment
    '((edge (0 1) (1 2)))))
(def next-view (read-view next))
;; Applying read-view to first still observes the earlier completed snapshot.
#+end_src

The declaration/export selection is fixed at preparation. Changing the
caller's checklist afterwards cannot change it. Reprepare when declarations
or export mappings change; data transactions on the same admitted program
reuse it. Handles remain scoped to the declaring fragment, so another
independently constructed fragment with identical public labels cannot
supply these relations merely by sharing their spelling.

Public views copy list and row spines. Repeated labels produce independent
copies, and mutating an answer cannot change another answer or a later read.
This is the existing public row ownership boundary; it is not recursive
cloning of arbitrary cell values. Prepared readers grant no source mutation
authority and retain no earlier solution.

=operator-session.ss= is the production consumer: opening a retained operator
prepares its output reader once; rows, successful append and successful batch
replacement apply it to the exact completed solution being published. The
existing Session admission, rollback and full transaction publication remain
the owners of updates. A failed batch does not replace the committed result.

=program/result.ss= already owns a private publication cache of ordered row
promises keyed by unchanged persistent row roots. Prepared queries use those
existing snapshots through =rows-of=; no second built-data cache is added.

* Prepared source transactions: bind authority to one retained Session

The read preparation above retains exported relation selection while applying
a supplied completed solution. Repeated writes have a different context:
the receiving Session owns source admission and publication. LeanPoo's
preparation-cache contract distinguishes a consumer view from publication of
the whole updated registry. That ownership distinction guides this native
change; its data updates are not LeanPoo registry edits.

=relational-session-prepare-transaction= accepts a Session and an ordered,

source handles. It reads no proposed rows, runs no engine and publishes no
state. It retains private handles rather than the caller's mutable checklist.

    (list (list edges 'raw-edge) (list blocked 'blocked))))

(def later (replace-pair (list '((2 4)) '())))
#+end_src

Application requires exactly one row batch per selected source, in checklist

* Own the lattice admission and publication protocol

Study native Gerbil =src/std/struct/lru.ss= for private final records, explicit
factories and typed =using= field contracts. Apply the ownership boundary to
=program/lattice-frontier.ss=: one table and one node per key, with exact
last-update sequence and a separately materialized output spine. Joining and
budgets belong to the engine, while membership/order belong to the frontier.
A private positional protocol needs no public generic hierarchy.

Keep caller semantics explicit. Source admission stages every accepted
occurrence; derived admission stages only effective changes. An equal value
can therefore affect source order without affecting derived order. Preserve
this distinction in the complete flow rather than deduplicating both callers
through an overly broad helper. Lookups leave ordering untouched. Clear state
only after publication, and keep held result spines independent of mutable nodes.

Unique arrivals already have the required order. Sorting after a key revisit
avoids allocation for every update; a linked-node attempt reduced allocation
but failed the repeated-key CPU gate. Choose the representation with matched
complete consumers and negative controls, not a shorter isolated helper.

* Carry accepted source ownership through update selection

A persistent source log and its ordered materialization have different lifetimes.
=program/source-snapshot.ss= now captures base/addition roots in private final
records, independently of caller source-state headers. The prepared cut carries
materialized rows and declaration views through execution and acceptance.
Session replacement, recovery, timeout replay and native engine source cuts use
this owner. Reuse neither admits rows nor skips per-occurrence budgets.

The accepted cut also supplies bounded equality evidence to update selection.
Evidence requires the exact candidate Program, exact original log roots and
exact materialized row root; foreign candidates and stale roots fall back to
ordered value comparison. Eligibility and transitive dependency closure remain
separate checks. This follows the Gerbil compiler's invocation-owned fact pattern
rather than adding mutable global facts or a parallel hierarchy of generic methods.

A materialization-only complete-consumer experiment failed its CPU gate. Avoid
promoting header allocation savings to a solver speed claim: carry the ownership
contract through the consumer that repeats comparison, then measure the entire
transaction including ordered public result reads. Keep rejected candidates and
small controls in the same fixed qualification contract.

The completed cut also owns a private native publication capsule, separate from
the public POO Result. =values= transfers both from the producer; exact Result
identity protects internal read-only consumption, while public reads detach
spines. Source-only seeding requires a complete rule-head absence fact and a
matching occurrence count after fresh admission. Equal source/result counts
alone cannot prove absence of derived facts. Revoking a retired engine's capsule
keeps ownership aligned with its adopted result without invalidating held cuts.

The complete accepted/rejected transaction consumers qualify substantial gains;
eager replay misses its unchanged CPU target and remains an explicit open item.
