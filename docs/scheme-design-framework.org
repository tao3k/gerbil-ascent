* Acceptance rule

This matrix defines the scope of design closure. An implemented interface,
a semantic argument, a passing discriminator and measured application benefit
are separate obligations. A row closes only the claim stated in that row.
The [[file:scheme-closure-contract.org][closure contract]] supplies the semantic limits; the
[[file:native-library-acceptance.org][Library acceptance contract]] supplies the general execution gates.
Historical receipts bind their own sources and do not certify later commits.

C4's finite universe argument applies to fixed sources, mappings and selection
constants. It does not extend to C5's integer generation. A finite lattice key
set is insufficient when values can improve forever. C7 binds supplied data;
it does not authenticate a producer or establish real-world completeness.

* Research decisions and remaining closure conditions

| ID | Design decision | Required falsifiable evidence | Status / dependency |
|----+-----------------+-------------------------------+---------------------|
| R1 | Admit general higher-order operators only with explicit domains, modes, captures, effects and monotonicity/height obligations | Reject escaped dependencies and out-of-domain derived rows; establish soundness for the stated IR, then compare independent finite models | Open; C4 is the supported subset, not a generic Datafun type theorem |
| R2 | Finite-domain declarations must validate inputs and every derived value, never silently clamp | Unbounded successor and increasing one-key lattice become admission rejection or explicit domain failure; complete in-domain closure agrees with oracle | Open; current C5 fails at operational bounds |
| R3 | General deletion requires multi-support and cyclic support semantics | Remove one of two supports, remove final support, break a recursive cycle; compare every transaction with full recomputation and measure work | Implemented native dependency invalidation for the checked DSL; custom providers and opaque callbacks recompute |
| R4 | Complete provenance needs an explicit recursive provenance algebra and certificate cost bounds | Independent witness enumeration on finite models, cyclic cases, tamper and size limits | Open; C7 provides bounded founded witnesses/finite replay |
| R5 | Architecture benefit must be measured separately from correctness | Same semantics, input set, dependency versions and budgets; operation counts and time/memory distributions | Open; focused native passes establish no speedup |
| R6 | Model validation measures comprehension of actual Scheme and reasoning, with actual native feedback after a response | Freeze tasks/source/invocation, score raw acceptance and semantic correctness separately, retain timeouts and status mismatches; compare reasoning and feedback conditions | Open; no preset semantic prompts, tutorials, answer prefills or repair loops |
| R7 | MRR Rust integration follows native and model acceptance | Preserve exact statuses, ABI limits and semantic authority through a byte-level binding; independent conformance on the accepted subset | Deferred until the preceding acceptance gates; no Rust runtime changes in this slice |

* Model interface policy

Why might an invocation contain text? Actual source, the user's task and a
transport request identify the computation being evaluated. They are not
permission to provide prewritten semantic explanations, expected answers,
few-shot examples or hidden correction rules. This work adds no such prompts.
A guard must expose the actual computation/status at response time rather
than teach a predetermined solution. The evaluation target is the model's
understanding of Scheme logic and its own reasoning ability. Any transport
format acceptance failure must remain visible separately from semantic accuracy.
A post hoc extraction result cannot replace the raw-interface acceptance rate.
Native correctness alone cannot close R6 or justify MRR integration.
