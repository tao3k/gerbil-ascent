* Study: stable engine-owned physical index entries

The installed Gerbil compiler's =optimize-base.ss:24-29= names its private
optimizer state and owns identity-keyed tables for types, classes, signatures
and methods. Identity lookup is appropriate after a stable object has been
resolved; it does not replace semantic equality at the initial resolution.

=program/index.ss= now applies that distinction to admitted immutable atoms.
Each engine retains separate all/delta structural column tables and lazy
identity tables. An atom's first indexed lookup resolves a shared column entry;
subsequent lookups reuse that same entry by atom identity. Different atoms with
equal columns still share the physical index. No row, expression value or
lookup result is memoized. Small relations and empty column sets retain their
existing bypass, so they allocate no identity table.

A private =physical-index-entry= record names its version and physical value.
Its stable identity survives incremental extension and replacement. The new
physical value is installed only after build/extend returns successfully;
=version=#f= means a failed cold build has no ready index and cannot be extended.
Delta version changes rebuild normally. The column-table traversal updates
owned fields instead of replacing table values and allocating version pairs.
Custom providers may return a new index object; every atom sharing the entry
then observes it. Entries and identity tables never cross engine boundaries.

* Feature: prepared general index key terms

=gerbil/compiler/optimize-call.ss:88= checks mutable bindings before substituting
lambda arguments. The relevant principle is to move only work whose inputs
are stable, while preserving observable evaluation. ASCENT's physical index
columns and admitted term descriptors belong to immutable declaration plans;
expression results and environment bindings do not.

=program/objects.ss= now records ordered key terms in the same traversal that
selects indexed columns and prepares binding terms. The private atom vector
contains relation position, raw terms, columns, binding terms and key terms.
The first four fields retain their meanings. Key terms refer to the same term
descriptors; they never retain computed expression values or engine buffers.
Selection still uses bindings from earlier clauses, rather than names first
bound within this atom. This costs one additional list spine per atom key in
the declaration cache, proportional to the number of selected columns.

After index construction, the general evaluator calls
=gerbil-ascent-index-key/terms= with that prepared list. It visits only the key
terms instead of repeatedly walking the full term list with =list-ref=.
Expression callbacks still run in column order on every lookup. Dynamic column
key construction and prepared key construction share one value operation for
literals, expressions and variables; missing bindings retain the same error.
The positive slot-based path continues to use its existing prepared slot terms.

The real index qualification module compares results and the complete
build/expression/lookup trace against the frozen evaluator. It also verifies
that declaration planning does not evaluate expressions, fresh variables are
excluded from key columns, and false values and missing-variable errors retain
their semantics. No provider callback is bypassed.

* Feature: lattice rows and term binding

=program/funs.ss= extracted a lattice key with two reversals and a
lattice value with another reversal. It now uses =butlast= and =last=,
with an explicit nonempty check for the private key helper. The
evaluator also calls key and value separately in some paths, so a
single extraction at the caller is a possible later measurement target
without adding a new public helper.

=gerbil-ascent-bind-row= is a compact state machine. Its invariants are
repeated-variable equality, pattern result arity, and shadowing order
of newly bound variables. A =match= rewrite is desirable only if those
invariants become easier to see and the errors stay stable.

Relevant qualification: repeated-variable, lattice, pattern, rule,
and invalid-program fixtures. Record values, row order, and errors.

** Checked binding and identity storage

=program/objects.ss= now retains raw atom terms for admission and
index-key planning, and prepares a separate binding-term list. A
=fresh-variable= term is permitted only when the name is absent from
earlier clauses and earlier terms of this atom. At row time that term
conses its binding directly. Repeated variables, pattern outputs,
expressions, and externally bound names retain the original checks.
This removes environment searches for first variable occurrences;
it does not change the public term grammar.

A separate experiment bypassed identity storage wrapping for the exact
built-in Set Provider without field callbacks. It was reverted because
matched whole-solve measurements did not qualify a stable gain. The
retained evaluator changes only the three atom-binding calls to use
prepared terms. Storage admission, duplicate accounting, budgets,
custom Providers, and field callbacks keep their original paths.

uses original raw binding terms, while both evaluators share current

* Feature: indexed relations

=table/funs.ss= builds bucket order by reversing the current relation
snapshot once and then prepending each row. This is intentional.
=hash-update!= with an empty-list default passed the index qualification
but was reverted after a broader test hit a time budget. The same
time budget failed after the revert, so that test does not attribute
the anomaly to either hash implementation. The existing standard
=hash-ensure-modify!= remains the clearer bounded choice here.
=gerbil-ascent-index-key= uses =list-ref= for each selected column;
its cost grows with both row width and selected columns. A single
pass over the row could help wide composite keys, but arbitrary
column order must be preserved. Use the existing index-program and
BYODS cases plus a matched wide-row probe before choosing an algorithm.

** Canonical single-column physical index lifecycle

The installed Gerbil compiler's =compiler/base.ss:150-174,198-235=
uses admitted binding shapes and native identifiers directly. Its
=runtime/hash.ss:475-505= selects hash implementations from equality
semantics. Applying these ideas here means removing a redundant
one-element key list throughout construction, extension and lookup.
It does not justify an =eq?= table: strings, lists, false and empty-list
values remain valid keys with structural equality.

=table/access.ss= now uses a plain native hash table for the canonical
one-column index. Composite and empty keys retain the existing path;
custom Providers still receive list keys through their original hooks.
Bucket order remains reverse-on-build and prepend-on-extension.
=core/positive-plan.ss= evaluates a single key value through the same
slot or expression helper used by the previous list-key producer.
Physical construction still precedes expression evaluation.

=program/index.ss= owns one engine's lazy all/delta caches and cache
versions. The evaluator owns admitted rows and publishes row/size/version
vectors. Extension reverses an admitted batch only when a cache exists
and the caller supplies reverse order. The 32-row threshold and retained
snapshot behavior are unchanged. =build.ss= adds one production module.
