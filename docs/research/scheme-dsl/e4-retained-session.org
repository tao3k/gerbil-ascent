* Question and source lesson
:PROPERTIES:
:CUSTOM_ID: scheme-e4-retained-question
:END:

The [[file:e4-positive-change.org][prior E4 probe]] propagates positive changes through a finite set
interpreter, but it rebuilds the old fixed point for every API call.
Does admitting a first-class transformer once into the existing native
Session retain the useful rule and relation state across calls while
preserving its finite set meaning?

[[https://www.cl.cam.ac.uk/~nk480/seminaive-datafun.pdf][Datafun S20]] studies a typed higher-order seminaive transformation for
its language (§§5–9). [[file:dbsp-b22.org][DBSP B22]] frames view maintenance as a stream of
snapshots and changes (§§1–3); its introduction notes that simply
reconstructing the full dataset from each change does not itself yield
an efficient incremental query. These papers motivate a *stateful
execution* discriminator. Their formal results do not prove this
Gerbil compiler, Session, or arbitrary Scheme procedure correct.

The local architectural finding is that =program/session.ss= and
=program/evaluate.ss= already own a retained, semi-naive engine. Adding
a second persistent store in =operator-change.ss= would duplicate that
owner. The new [[file:../../../program/operator-session.ss][operator Session facade]] instead lowers the inspectable positive
graph through the existing fragment/admission path. Its generated input
label is private to one instance; captured finite sources stay fixed.

* Operational contract
:PROPERTIES:
:CUSTOM_ID: scheme-e4-retained-contract
:END:

#+NAME: scheme-e4-retained-operations
| Operation | Returned observation | Execution boundary |
|-----------+----------------------+--------------------|
| =relational-op-open-retained= | Completed first result | Compile, admit and solve once with explicit input/derived/output budgets |
| =relational-op-retained-append!= | Before, after, newly added output rows | Checked source row; positive native Session may reuse retained relation state |
| =relational-op-retained-replace!= | Before, after, added and removed output rows | Checked full source replacement; native Session recomputes for withdrawal |
| =relational-op-retained-replace-sources!= | Before, after, added and removed output rows | One checked batch of exported graph sources; commit follows a complete native solve |
| =relational-op-retained-rows= | Copied rows of last completed solution | Caller mutation does not rewrite the retained result |

The Session owns recovery after a failed update. The facade publishes a
new =latest= solution only after =relational-session-run= completes. It
does not admit caller procedures into rule evaluation. Its source is
one explicit transformer parameter; the original append and replace
operations address that parameter only. A duplicate input row
can consume the input-fact budget while adding no output row.

The later batch API extends this boundary: callers may replace the
explicit input, addressed by =relational-op-retained-input-label=, and
any captured source with an exported label. The checked layer copies
every row and rejects unknown, derived, or duplicate labels before
evaluation. The native Session constructs a prospective snapshot and
runs it in a separate engine; only success installs the new engine and
completed solution. This is an atomic multi-source *recomputation*,
not DBSP's signed-change circuit or an incremental deletion result.
DBSP §4.1 (PDF p. 5) uses integer-weighted sets, with negative weights
representing removal; its join-change equation in §3.3 (PDF p. 4)
includes old/new, new/old, and new/new terms. Those results motivate a
future deletion design, but do not license applying an insertion-only
set derivative to the present batch API. The transaction guarantees
snapshot consistency while that algorithm remains an open gate.

The composed Scheme language now uses =relational-session-transaction!=
for =(fragment label rows)= updates spanning *different* fragments.
Named =relational-program= sessions expose =relational-program-transaction!=
with =(name . rows)= entries. Both reuse the same checked row boundary
and the native Session's prospective solve. The [[file:deletion-h18.org][H18 deletion reading]] explains
why recursive support counts or a different change algebra would be
needed before replacing that full recomputation.

The [[file:../../../t/qualification/scheme-operator-retained-test.ss][qualification test]] covers every mask of six directed three-node edges.
For each of the 64 initial graphs it compares the old result, insertion,
duplicate insertion, and withdrawal with an independent
Floyd–Warshall closure and set difference. Other cases exercise fixed
captured input, finite mapping and selection, invalid row/replacement,
an exceeded output budget, prior snapshot stability, and mutation of
a returned row copy. This is bounded evidence for the implemented
grammar, not a proof of general higher-order incrementalization.

A second 64-mask check updates two source relations feeding a nested
fixed point. Expected output comes from an independent finite closure
over their union. An over-budget batch, an invalid row, and a repeated
source label fail; a later update of only one source proves the other
source and the earlier completed result were retained. This tests the
transaction's semantic boundary, not its update latency.

* Matched local experiment
:PROPERTIES:
:CUSTOM_ID: scheme-e4-retained-probe
:END:

The [[file:../../../t/performance/scheme-operator-retained-probe.ss][probe]] compares two executions of the *same* transformer and grown
graph. =retained= opens the old graph outside the timed region, then
times one checked append and result query. =fresh= times opening and
solving the grown graph from scratch. Both results are checked against
an independent finite closure outside the timed region. Each case
warms both paths and alternates their order for five paired samples.
The intended comparison is update latency after a materialization
exists versus new materialization; it does not compare two equally
initialized engines or include the retained path's initial open cost.

A second chain-24 sequence includes initial materialization and eleven
successive insertions. The retained path opens once and appends; the
fresh path opens the same grown graph at each revision. All twelve
snapshots per path are checked against independent closure sets outside
the timed region. After warmup it alternates three paired lifecycle
samples. This includes startup for both methods, but does not measure
resident memory or isolate rule execution from compiler startup.

The lifecycle medians favor retained in these two runs, while sample
distributions overlap and the repeat retained median shifts greatly.
The result supports a local update-latency hypothesis, not an
asymptotic, allocation, or cross-language performance claim. The fresh
path pays compilation/admission/startup costs that the retained path
already paid before timing in the *single-update* cases; both paths pay
their initialization cost in the lifecycle case.

Whole-snapshot recomputation remains the withdrawal baseline; the

pass before replacing it.

* Remaining discriminators
:PROPERTIES:
:CUSTOM_ID: scheme-e4-retained-next
:END:

- Repeat lifecycle measurements under controlled load and record
  allocation/resident memory, which the current probe does not measure.
- Separate native indexed rule work from compilation and admission with
  reproducible phase receipts before attributing a speed difference.
- Give source deletions and changing nested fixed points their own
  semantic and cost arguments. The current replacement path recomputes.
- Keep the finite interpreter as a semantic check for operator rules;
  avoid claiming it shares the native Session's internal algorithm.
