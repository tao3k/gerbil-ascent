#+TITLE: Resident Scheme process owners and production throughput acceptance
#+DATE: 2026-10-20

* Scope

This change removes the process-global single SERVICE queue from the Scheme
application binding. It does not identify test preparation time with runtime
throughput. The original preparation failures and performance ledger remain
separate evidence; no timing threshold, heap limit, semantic corpus or formal
control is removed by this change.

* Production execution

=ascent_scheme::ProcessPool= owns a fixed population of exec-isolated workers.
Each worker initializes the statically linked application with the existing
=gerbil-scheme-rust= single-processor initializer, checks its actual processor
population, and keeps the VM on its original OS thread. A handshake checks the
child PID, protocol version, owner domain and compiled Scheme/build identity.
There is no per-request process spawn, copied dynamic-library image, second VM
inside a worker, or runtime Rust/C compilation of user DSL.

An =Engine= lazily owns one resident process. A caller-owned =ProcessPool(12)=
explicitly owns twelve resident VMs; no hidden global pool multiplies test
processes. Its engine clones and all
module, value, inference, explanation and provenance leases retain that owner.
Explicit callers can select =pool.owner(index)= with =Engine::on_process=;
rebinding creates fresh native module caches and lease tracking. Rust thread
capacity remains a separate setting. A single engine's opaque Scheme state is
not concurrently entered by twelve threads.

Worker setup, GC roots, native conversions and teardown remain upstream-owned.
The application transport carries only owned typed data using binary bincode
frames. Exact integers, real bit patterns and typed failures are preserved;
no JSON or Scheme heap pointers cross process boundaries. Python calls the
same Rust owners through PyO3. Its child entry imports the same extension with
the caller's import paths; no Python FFI implementation is added.

A worker's exported identities use a distinct domain modulo 2^32. Allocation
checks the u64 ceiling before publication, never wraps, and never silently
restarts a failed worker with recycled handles. Foreign native references
therefore cannot accidentally resolve to the same local ordinal in another VM.
Logical fact/work limits remain the existing typed session contracts; native
per-VM capacity bounds remain in the original Scheme implementation.

* Interruption and publication

Controlled requests retain their original parent Control. Every child
checkpoint, including acceptance and recovery suspension/resumption, obtains
its decision from that exact original controller. The implementation does not
batch away budget or clock checks. Accepted publication retains its existing
linearization semantics; cancellation cannot turn a committed update into a
canceled response. Disconnected callers retain the original operation-specific
cleanup branches for module, value, source-result and explanation leases.

Checkpoint transport is a possible performance cost, not an admitted optimization.
The throughput experiment counts it explicitly. A dead worker is revoked;
other worker processes remain independent. Normal owner teardown closes the
socket and reaps the child; bounded fallback cleanup targets only that child.

* Semantic qualification

The existing complete native binding/archive suite continues to run with twelve
Rust test threads and zero retries. Additional production-path coverage checks:

- Twelve distinct process PIDs, domains and actual single-processor VMs.
- Persistent lexical state, real callable application and complex native values.
- Native handle domains and rejection of foreign references.
- Cancellation during a running Scheme callback and recovery on that same VM.
- Complete reachability, independent provenance replay, source-generation
  revocation, input-fact rejection and timeout/cancellation rejection.
- Real child-process failure without handle recycling or another VM's revocation.
- Exact binary numeric/error round trips and rejection of truncated replies.

The transport and scheduler are not claimed to have complete Lean source
refinement merely because these tests pass. Existing Lean/Quint checks must
still pass independently. Whole-VM cumulative allocation and previous compiler
source-cost refinement gaps are not closed by adding process isolation.

* Fixed-work production measurement

The =process_throughput= Rust benchmark calls the public Engine, Module,
ModuleValue and Session interfaces. It loads the original Scheme DSL once per
session, warms it, then continuously replaces distinct input facts and obtains
complete results. The independent Rust oracle checks every transitive closure
tuple before an observation is published. All measured requests use the
production default work/fact/time ceilings. No Rust Ascent production dependency
or alternate evaluator is introduced.

The matrix has Scheme populations 1, 3 and 12, each with one processor per VM,
and a shared Rayon pool with 1, 3, 6 and 12 threads. Every configuration receives
the same total work, twelve sustained clients and five predetermined samples.
Scheme clients keep independent admission resources; Rayon clients explicitly share the specified
Rust pool. Startup/loading/warmup are recorded separately from measurement.

Per-request traces retain latency, batch-relative completion time, replacement
cost, run/export cost and the full-answer digest. Summary records include
throughput, p50/p95 latency, native call overlap, queue time, service time and
checkpoint counts. VM-call overlap includes waits inside an ABI call and is not
a claim of twelve simultaneously executing physical CPU cores. Actual parallel
benefit is the measured throughput ratio. Rayon ratios are reported against both
one VM and one Rayon thread.

The Python driver performs orchestration and admission only. It records binary
hashes, source head, CPU population, every planned run and foreign-compiler
observations. It retains failures, does not retry them into admission, and never
normalizes a slow measurement. Startup and teardown remain visible in process
wall time. An optional input of the existing macOS experiment workflow runs this
matrix on the three-core runner after all compilation; it adds no mandatory ABBA
or new required CR performance threshold. Existing three-core/240-second source
qualification and twelve-thread native tests remain unchanged.

* Native retirement root cause and phase correction

The buffered candidate completed all 56 native Cases in 159.898 seconds with
twelve test threads and zero retries. Its strict retirement audit still failed:
several workers reached =vm-cleanup-begin= and were killed by the newly introduced
two-second supervisor timer before =vm-cleanup-end=. That run remains rejected
as full acceptance despite its passing Case assertions.

A bounded twelve-process diagnostic captured the native stack inside
=___cleanup_dyn_module -> dlclose -> notifyDebuggerUnload=, including synchronous
dyld notifications. Only the selected owned supervisor was paused to preserve
the child for sampling; this invalidates timing admission. That child completed
native cleanup and exited normally. Its observed 4.476-second diagnostic interval
includes the sampler and is not a performance measurement. The other eleven
children still hit the artificial timer; their parent test exit status zero is
not evidence that those children shut down correctly.

The repair distinguishes active request drain from quiescent native destruction.
The existing two-second drain deadline still bounds active or broken requests;
it is not restarted to grant an additional interval. Once the request queue has
quiesced, the upstream runtime completes its ordinary destructor and the parent
reaps its actual status. No =mem::forget=, immediate process exit, skipped GC or
successful label for a killed VM is used. Enclosing test/CI deadlines remain
unchanged. Pool destruction initiates independent unleased retirements together,
while engines/values retained outside the pool keep their owner process alive.
A separate regression covers natural cleanup longer than the artificial timer.

The installed Python pool factory reuses the original Engine constructor's
backend and source/input ceiling validation. Its qualification explicitly selects
=scheme=, checks both retained ceilings, and still exercises twelve resident VMs.

* Checkpoint transport experiments and exact rejection records

A diagnostic with twelve simultaneous copies of the 3,000-complex-cell Case
located its timeout in =execute=, rather than result lookup or graph export.
All twelve copies failed under their unchanged limits. This is diagnostic
local stress, not a clean-host throughput receipt. It does not identify a
single source function as the entire root cause.

The first shared-checkpoint candidate was rejected. Its complete scheduled
native run recorded 60 Cases: 58 passed, the complex-cell Case timed out, and
the process-failure Case was interrupted after a confirmed peer-exit hang.
Total supervisor elapsed time was 580.658 seconds. Passing assertions and
partial measurements from that candidate are not acceptance.

Native sampling found the parent polling during module expansion. The revised
transport therefore uses the shared exchange only for =source-run= and
=source-replace=. Loading, expansion and other operations retain the sleeping
binary socket exchange. The shared exchange sends every signed work transition
to the original bound parent Control, waits for that exact decision, and only
then returns to Scheme. It does not cache positive decisions or sample the
cancellation clock less frequently. The bound entry avoids the process-global
weak-entry lookup, while executing the same =checkpoint_scope= body.

The peer-exit hang had a platform-specific application cause. A minimal Darwin
socket-pair probe after closing the peer reported zero events for =poll(events=0)=
and =revents=17= for =poll(events=POLLIN)=. The failed child was already a zombie;
the parent had not observed EOF. Liveness now declares read interest and peeks
without consuming protocol bytes. Regression coverage checks an idle live peer,
a pending valid frame, and EOF after closing the peer. No SDK patch is needed.

The shared file contains only a private, fixed-size atomic request/decision
slot, never Scheme pointers. Each process owns its own mapping lifetime.
Acquire/release publication orders the signed work payload and response;
a subsequent checkpoint cannot overtake its decision. The application still
uses the released upstream VM initializer, GC and value conversions. This is
an application control transport, not a second Scheme evaluator.

These tests and implementation arguments are not a Lean proof of Rust/POSIX
weak-memory or process-lifetime refinement. That source-refinement gap remains
explicit. Existing formal CI is an independent obligation, and its success
alone does not close this new transport's source-equivalence boundary.

* Scoped candidate rejection and request-generation repair

The scoped candidate's complete local run recorded 62 Cases in 370.815 seconds:
60 passed and two failed, without forced-stop, shutdown-error or leak markers.
The actual twelve-process failure/recovery Case passed. The failures were an
ASP broad-public-function finding in =serve= and the complex-cell Case returning
=Closed= during execution. The worker has been split into initialization,
execution and lifecycle steps; neither the style rule nor Case was disabled.

Source audit also identified a missing request-generation guard in the shared
slot. Reusing phase values alone allowed a previous =COMPLETE= observation to
be confused with a new ABI call. The child now publishes the current original
Control identity after resetting the phase; the parent acquires that identity
before observing the phase. A regression leaves an old completion in place and
checks that it cannot finish the subsequent request. Interrupted nonblocking
peer probes are handled transparently instead of being converted to a closed
controller. These are concrete repairs, not a claim that the earlier =Closed=
observation has been completely explained before the next native run.

The Linux follow-up replaces the shared slot's active-yield wait with a bounded
process-shared =FUTEX_WAIT=/=FUTEX_WAKE= exchange. It never uses the process-private
futex flag, because each process maps the same backing file independently.
The wait compares the observed atomic phase, preventing lost wakes. Generation
publication precedes observation, and interrupted/spurious wakes recheck the
protocol. A one-millisecond wait interval detects a dead peer; it is not an
execution allowance and does not replace any checkpoint decision. The original
parent controller still runs once for every signed work transition. This
scheduling repair requires fresh Linux semantic and current-head CI receipts;
Mac success alone does not admit it.
