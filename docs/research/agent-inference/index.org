* Question and scope
:PROPERTIES:
:CUSTOM_ID: agent-inference-research
:END:

How should a reusable *deployment-time* Library improve an LLM's
reasoning without changing model weights?  Search can supply current
evidence; Datalog can check relational consequences; other checkers
may test arithmetic, code, plans or hypotheses.  The common path is
an attempt with a named input, candidate proposal, checker observation,
bounded explanation, and possible revision.  The
[[file:../../scheme-relational-dsl-design.org][Scheme DSL overview]] describes the internal relational language;
this ledger studies the *interaction protocol* around the Library.
The sources below use different logics and workloads.  Their results
are design evidence, not proof that our Library already has the API.
The [[file:reasoning-language-formal-agenda.org][reasoning-language and formal agenda]] ranks the ASCENT/PL language
papers, maps the MRR boundary, and states the remaining Lean/TLA+ gates.
The first concrete checker is =gerbil-ascent=; POO Flow owns workflow
composition, tool selection and runtime handoff.
The implementation priority is the direct Library contract for LLM
candidate reasoning alongside the internal Datalog core.  Serving
adapters such as [[file:serving-sglang-vllm.org][SGLang/vLLM]] follow that
contract; they are lower priority than its executable Scheme fixture.

* Cross-source inference
:PROPERTIES:
:CUSTOM_ID: agent-inference-synthesis
:END:

The [[file:2026-logic-ai-screen.org][code-anchored research screen]] joins the Ascent, BYODS and Datafun
lineage to real knowledge-graph questions, candidate-rule synthesis and
the actual Scheme owners. It puts semantic scope, independent results
and workload quality before publication year.

The first model comparison preserves the raw, frozen =propose= output,
then measures =inspect=, =execute= and =explain= as separate outcomes.
A later revision is a separate experimental condition, not evidence
that the model understood the rule on its first attempt. The general
workflow can use =observe -> propose -> check -> explain -> choose
another step or stop=. This is our synthesis, not an API these papers
jointly prescribe. DB26 shows that fixing syntax and declarations can
still leave recursive semantic errors; ML26 shows that executable
constraints can also be specified with the wrong scope.
P18 shows why explanations are a separate query over provenance rather
than a natural-language retelling of the returned row.
The Library supplies evidence and checks at inference time; model
judgment remains distinct from a checker result. Preserve the raw first
proposal before evaluating any optional follow-up attempt. No model
retraining or modification to its learned reward mechanism is claimed.

#+NAME: agent-library-contract-draft
| Stage | Library input | Library output | Limit of the claim |
|-------+---------------+----------------+--------------------|
| Inspect | Candidate declarations plus named source snapshot | Structured syntax, schema, mode, dependency and bound diagnostics | A valid program can still express the wrong intent |
| Execute | Accepted candidate program, exact snapshot and budget | Complete rows or typed partial/failure status | Completion proves the declared program's result only |
| Explain | Result/goal, snapshot, rule program and bounds | Supporting witness or finite-graph absence/cut with status | One witness is not all provenance; general recursive Why-Not needs explicit semantics |
| Revise | New candidate against same or explicitly changed snapshot | New diagnostics and result, linked to attempt | No automatic promotion to source authority |

Other reasoning modes use the same attempt/result envelope, but each
checker declares its own semantics, supported goal types, bounds and
explanation limits.  Datalog is the first backend, not a claim that
every model thought has a Datalog encoding.

The response must distinguish =rejected=, =complete=, =partial=,
=unknown=, and =unsupported=.  Every returned answer or explanation
names its input snapshot, program identity, limits, and whether its
support is complete.  In =gerbil-ascent= these are *candidate* facts
and explanations.  MRR retains semantic admission and canonical lineage;
POO Flow owns caller context and effect handoff.  The Library does not
ask a model to mutate the fixed-point state during one solve.

* First executable discriminator
:PROPERTIES:
:CUSTOM_ID: agent-inference-gate
:END:

Use one graph task with two source generations and an LLM-like
proposal transcript: (1) a valid base + recursive reachability rule,
(2) an invented undeclared helper relation, (3) a wrong recursive join
that compiles, (4) a query for present and absent pairs, and (5) a
source edge withdrawal.  Check field-specific diagnostics; exact
complete rows against an independent finite graph model; one
supporting path and, after complete closure, finite-graph absence/cut
evidence; unchanged
old snapshots; and no candidate-to-admitted promotion.  Record
repair turns, token-sized feedback, wall time and model-independent
semantic outcomes separately.  Only a later model experiment can
claim that the interface is friendly to LLMs.

For that later experiment, freeze the same model, task corpus, search
index, source revisions and tool budget.  Compare =search + model=
against =search + Library inspect/execute/explain + model=.  Score
answer correctness, cited-source coverage, unsupported conclusions,
why/why-not fidelity, abstention, repair turns, latency and cost.
Do not infer a change to the model's learned reward function from an
improved deployed answer: the intervention is external evidence and
feedback at inference time.

* POO Flow workflow and optional framework connection
:PROPERTIES:
:CUSTOM_ID: agent-inference-workflow
:END:

POO Flow already separates workflow declarations and strategy/runner
execution through POO objects.  Its tutorial includes a composed
TensorFlow train/infer *external task descriptor*, which shows a
workflow can carry training tasks without making Scheme the trainer.
For our deployment-time case, a proposed POO Flow workflow would:

#+NAME: agent-reasoning-workflow
| Step | Owner | Output |
|------+-------+--------|
| Select task, capability, budget and sources | POO Flow | Scoped request |
| Search or observe | Source/tool owner | Versioned candidate evidence |
| Propose a reasoning step | LLM/model caller | Candidate facts, rules, query, plan or hypothesis |
| Inspect and execute | Gerbil Ascent for relational case; other named checkers otherwise | Typed diagnostic, bounded result, completion status |
| Explain and decide next step | Checker returns witness/gap; model caller judges; POO Flow routes | Revised attempt, abstention or bounded answer |
| Admit or hand off | MRR/source owner and separate runtime policy where needed | Admitted evidence or authorized effect receipt |

This is a workflow *proposal*, not an implemented cross-repository
integration.  It does not turn the Library into a model-step scheduler or
the training framework.  If a training/inference framework is chosen,
first test a discrete adapter that consumes complete, bounded candidate
outputs and explanations under exact source/program identities.  A
differentiable layer is a separate research path: [[file:scallop-s23.org][Scallop]] shows
why weighted provenance and gradient semantics would be required.
An FFI or tensor conversion alone does not supply those semantics.

For the SGLang/vLLM serving ecosystem, the first path is an external
tool adapter in the POO Flow application loop.  Both servers expose
tool-call proposals through their OpenAI-compatible chat interfaces;
the application executes the Library call and returns its observation.
The [[file:serving-sglang-vllm.org][serving interface study]] records official
documentation, owner boundaries and an experiment that compares the
same candidate protocol on both backends.  Model-serving support does
not itself validate LLM-proposed facts, rule meaning or evidence admission.

* Reading order

Start with the [[file:2026-logic-ai-screen.org][core screen]] and [[file:matlogic-ml26.org][ML26]] for real-KG
scope and witnesses, then [[file:datalogbench-db26.org][DB26]] for generated rule correctness. Read
[[file:../scheme-dsl/byods-b23.org][B23]] and [[file:../scheme-dsl/flowlog-fl25.org][FL25]] beside the Scheme Provider, planner and Session
code, followed by the [[file:../scheme-dsl/datafun-f16.org][F16]]/[[file:../scheme-dsl/datafun-s20.org][S20]] functional boundary. The
[[file:../scheme-dsl/mono-types-x25.org][X25]] reading tests whether a first-class container can preserve that boundary.
[[file:pug-p18.org][P18]] gives the separate explanation semantics; [[file:scallop-s23.org][S23]]
frames the optional training-framework question.
For an actual deployed-model interface, read
[[file:serving-sglang-vllm.org][SGLang/vLLM serving research]].
