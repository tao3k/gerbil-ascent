The production =Runtime= now boots with the upstream root owner initialized.
Its existing hybrid benchmark loads a small trusted module through the public
=module-source-open= and =module-call= interfaces, without an extra VM or a

The medians are computed independently per field. They are not an additive

reachable or prove that removing an expander cache preserves future imports.

The next investigation is therefore the retained root set and GC behavior
across trusted module loading, not another rewrite of UF component insertion
or another C ABI scheduler. The complete-list representation still allocates
fresh row and result spines for every read. Streaming, numeric transport,
shared mutable row tails and dividing a batch by 32 do not satisfy this gate.
Any candidate must preserve those ownership and publication semantics and
then pass the original 100-observation strict gate.

** Physical pair layout before and after collection

In the frozen =ea114fc3:lib/mem.c=, =mark_array= follows body slot
zero when it forwards a pair. =include/gambit.h.in= assigns that slot
to the cdr. The later =scan_and_advance= fast path reads the remaining
slot, the car. This lets one GC gather a previously interleaved outer
spine into runs before it copies the tuples referenced by its cars.
Heap-chunk markers and section boundaries interrupt those runs.
=dense_outer_spine_strides= proves the idealized offset difference
between contiguous construction triples and an adjacent copied spine.

A read-only C observer compiled via =gerbil build= traverses each
complete ordinary list at the call boundary. It checks the two-pair
row shape and counts links whose endpoints are physically one pair
width apart. It returns only counts and retains no addresses across a
GC. For each width, native =gerbil test= observed 24 complete outputs
before and after one explicit collection with the output held. The
GC count confirmed exactly one collection between probes and none
inside the second probe. The original independent dense-cycle oracle,
default live ratio, 2 GiB maximum and 90-second watchdog applied.

| Vertices | Outer links | Adjacent before / after | Adjacent tuple pairs before / after | Adjacent outer-to-tuple pairs before / after |
|----------+-------------+-------------------------+-------------------------------------+-----------------------------------------------|

|      512 |      262143 | 0 / 259058              | 262144 / 259059-259060              | 262144 / 0                                    |

* Gambit allocation entry points and detached pairs

The frozen =ea114fc3:lib/mem.c= implementation of =___alloc_scmobj=
dispatches on its processor argument. A null processor selects
=alloc_scmobj_perm=. A live processor selects =alloc_scmobj_still=,
which allocates a separately reference-counted still object, charges
the VM's still occupancy, and may run =___garbage_collect= before
returning. The C pair constructor calls this interface for each pair.
Releasing the C root lets Gambit reclaim a still pair. It does not
turn it into a movable pair.

The generated Scheme allocator instead places ordinary pair cells in
the processor's movable sections. =___heap_limit= can consume an
existing free section or admit a new one using the VM's available
capacity. When it cannot admit a section, it requests collection.
The public C allocation entry has no movable reservation variant.
Passing a nonzero still-object request into GC changes the resize
calculation and belongs to the still allocator's accounting protocol.
The measured terminal-still control above already charges this path.

This rules out replacing the current builder with a simple C allocation
wrapper that supplies the same movable pairs in bulk. The movable
payload and the fixed live roots remain separate costs. A runtime
intervention would need independent validation of heap accounting,
interrupt polling and ordinary pair lifetime before the full-export
gate could qualify it.

** Restoring a setting does not restore allocator state

The installed SDK uses Gambit =ea114fc3=. Its
=lib/_kernel.scm:##set-min-heap!= calls =lib/setup.c:___set_min_heap=,
which writes the process-wide setup value. It does not grow the
current movable interval. The next =lib/mem.c:resize_heap= reads that
value during collection, then combines the computed target with the
maximum of the VM's last 16 successful resize targets. The existing
section cap and overflow checks still apply. The ring gets the new
target only after a successful resize. =___heap_limit= admits existing
or available sections and requests a collection when those are
exhausted. The source exposes no call-local grow-and-release operation
through these paths.

Even on the current single-VM path, =dynamic-wind= can restore the
setup value without restoring the mapped sections or the resize ring.
An export can therefore leave a larger target that another green
thread's allocations use. The Lean obligation
=restored_minimum_retains_resize_target= models the newest-first view
of this ring and the carry-over until 16 newer successful resizes.
The seventeenth later collection can shrink if every intervening
target is lower. The proof does not claim that an actual shrink is
always possible, since surviving allocations can require the space.

Generational collection can target short-lived result pairs without
revisiting all long-lived roots on every renewal. A private region can
reclaim scratch objects at the end of construction, but these published
mutable pairs escape that region. Supporting either mechanism here
requires native reachability, write-barrier or ownership evidence.
In the frozen =mem.c=, =mark_array= forwards ordinary =MOVABLE0= objects
and the scan path visits their fields. The native object layout has one
movable generation. The existing C still-object allocator and process
setup setters do not provide a nursery or a barrier that could preserve
old-to-new references for a minor collection. See
[[https://www.cs.princeton.edu/research/techreps/671][Appel, Simple Generational Garbage Collection and Fast Allocation]] and
[[https://www.cs.cmu.edu/afs/cs/academic/class/15745-s06/web/handouts/tofte-popl94.pdf][Tofte and Talpin, Stack of Regions]].

The isolated =gerbil build= and =gerbil test= counterexample read the
actual ring maximum and mapped section count. The Case and Harness
passed within the 90-second watchdog, with the 2 GiB ceiling and default
live percentage verified. Setting the temporary 1 GiB minimum alone
left 192 mapped sections. The next collection enlarged that to 1,169.
Restoring the original minimum left 1,169 sections. The sixteenth
collection after restoration removed the high value from history and
still left 1,169 sections. The seventeenth collection returned to 192.
Mapped sections times section size plus still occupancy stayed below
the cap at every observation. The diagnostic times no export and
introduces no library setting change. The locked LeanPoo Guard also
completed the full 183-job model build, including the retained-target
and 512 renewal theorems. Evidence:
=.cache/ascent/yuanxu-v0.1.0/restored-heap-minimum.FSxSPs/=.

The frozen header also exposes an internal =custom_msection_alloc_=
field on the VM. In =mem.c:next_msection_without_locking= it is a

** Ownership of interior pairs after publication

The public result is an ordinary mutable list. A caller can keep a
row, a tail of that row, or a tail of the outer spine after dropping
the original head. The reachability graph is directed from the head
toward those cells. Death of the head gives no evidence about roots
held at an interior cell. The Lean counterexample
=unreachable_export_head_does_not_certify_interior= supplies a caller
root that reaches the terminal pair but cannot reach the result head.
This is why a weak reference or finalizer on the outer head cannot
certify that all three pairs per row can be reused together.

The frozen Gambit collector decides will executability in
=mem.c:determine_will_executability= from the testator's own strong
reachability. =process_wills= then marks that testator for delivery.
=lib/_kernel.scm:##will-execute!= clears the will and passes the
testator to its callback. None of those steps certifies exclusive
ownership of descendants. A native control holds only a terminal
pair and has a will on the head attempt a write to that same cell.
The caller saw that write after the head was finalized, while a
later real export still had the original values. Both 384 and 512
Cases passed and the native process exited zero under the existing
2 GiB limit and 90-second deadline, with Case, Module, Harness
and final markers.
No pooling or finalizer is installed by the library. Evidence staging:
=.cache/ascent/yuanxu-v0.1.0/export-interior-owner.O9oV0x/=.

The converse shortcut also fails for mutable results. Watching only a
row's terminal pair relies on the row head continuing to reference it.
In both native 384 and 512 Cases a caller used =set-cdr!= to detach the
terminal cell and kept the row head. The terminal will was delivered;
the caller could still read and mutate its row head, and the next full
export produced the original ordered row. The guarded Lean theorem
=mutable_pair_reuse_requires_watch= generalizes this counterexample:
hold any unwatched cell as the sole caller root and overwrite its
outgoing pair fields with scalars. All watched cells can become
unreachable while that cell stays live. The theorem concerns a reuse
protocol that relies solely on the death of watched cells. A protocol
with additional lifetime authority requires its own proof.

controls. The focused WeightedExportCapacity proof and all 185 Lean

*** Isolated forwarding kernel for the pair graph

The control calls the production UF capture and complete list export.
It encodes the ordered binary rows into a flat pair graph with two
64-bit fields per cell and integer references. The measured operation
clears a private forwarding array, copies reachable pairs into a
preallocated buffer and rewrites their edges. Capturing the Scheme
list, validating copied rows and logging are outside the timing.
The graph buffers are held by Scheme but contain no Scheme pointers.
This experiment prices the forwarding loop separately from native
root discovery, real object relocation, promotion, barriers and GC.

The first implementation scans both edges of each copied pair from

*** Remember incoming slots when forwarding a pair

*** Cost of retaining blocks of published pairs

An allocation region that never moves survivors could reclaim a
block once all its objects die. This avoids rewriting the slots
pointing into a retained block, at the cost of holding unused space.
The public list contract allows a caller to retain isolated terminal
pairs from arbitrary rows. In the extreme, one such pair keeps each
block in use. A mark-region design such as Immix addresses this
problem with finer allocation lines and selective evacuation.
See [[https://www.mmtk.io/assets/pubs/immix-pldi-2008.pdf][Blackburn and McKinley, Immix, sections 3 and 4]].

The Lean model =one_survivor_per_block_charge= proves the whole-block
charge for one surviving pair per block.
=pinned_blocks_refuse_next_export= gives the consequent allocation
condition: under a fixed capacity, the unpinned part must cover the
next fresh result. These laws count storage only. Their premises
describe a block allocator that admits no reuse inside a retained
block.

The native observer traverses the real detached list, selecting one
terminal pair per logical 4 KiB header block and retaining those
pairs in an ordinary Scheme vector. It drops the result head before
collection. Each retained pair has an empty cdr and a distinct
caller-written value. The native check validates all retained pairs
after collection and checks a fresh export for independence.

this control. =sparse_512_retention_exceeds_cap= checks a conditional
replay: if 114 results occupy disjoint sets of the measured 4,609

** Layout-only capacity envelope

The preceding renewal estimate subtracts assigned sections, the

* Ownership of the native complete-export collector

The bare native Test tool retained 86.21 MB before loading the UF
fixture. The module-registry controls above identify substantially
less exclusive storage than that figure. In particular, the observed
expanded bodies can still be needed by native evaluation, macro
expansion and reload. Keep these runtime roots under Gerbil's
ownership.

In ASCENT, =gerbil-ascent-trrel-uf-freeze= borrows immutable member
spines. The complete rectangle export needs the frozen descriptor cut
only. The generated Scheme for the existing export receiver already
captures just that cut. =materialize-rectangles= keeps the STD
=with-list-builder= within the export invocation and walks the
descriptors directly, so the collector no longer escapes through a
=for-each= callback. The list builder still allocates an independent
outer cell for each freshly constructed tuple. At widths 384 and 512,
a 32-export batch therefore still requires at least 324 and 576 MiB
of tuple and outer cells, respectively.

=rectangle_export_preserves_runtime_and_cut= in
=WeightedExportCapacity.lean= models the ownership boundary. A cell
lost after removing query-planning reachability must have been
reachable through that planning state, and must be unreachable from
both the descriptor cut and the runtime. The statement supplies no
native byte estimate and the query visitors can retain their own
plans while a view remains live.
