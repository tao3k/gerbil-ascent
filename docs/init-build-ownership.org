#+title: Build Ownership Audit

* Ownership

=init.ss= selects the top-level Module declarations through =:load-modules
"."=. The root =build.ss= is Gerbil's package hook and declares the ABI binary
targets. =gerbil build= and =gerbil test= own native compilation and test
execution. =build-modules.ss= and the old =modules/= declaration directory are
removed; no forwarding modules or replacement catalogue are provided.

* Removed mechanisms and consumers

- Deleted =bindings/artifact.ss= and its publisher, generation/directory scans,
  source inventory, compiler-output replay and receipt-driven invalidation.
- Removed =libascent.json= production and consumption, the Rust =artifacts=
  feature/module, publication/validation APIs and legacy extension wiring.
- Removed the private =configure-syntax= endpoint and the application rewrite
  of Gerbil's =load-module=. Isolated owners pass integration library load paths directly.
- Deleted the local cross-profile archive cache, lease/copy layer, input
  snapshotter, ledger, build-admission policy and their obsolete tests.
- Deleted =interface/build-identity.ss= and its source/runtime directory scans.
  Existing worker handshakes now bind the actual integration library-built archive digest.
- Removed the linked-development-image alternative from the test driver.
  GxTest keeps the native command, arguments, heap and exit propagation.
- Removed dead build-manifest benchmarks and deleted-test registrations.

These implementations were removed, not moved to a different directory or
retained behind a feature flag. Their removal does not weaken Gerbil/Yuanxu
source guards, integration library compiler checks or independent inference/provenance tests.

* Existing native Rust boundary

=ascent-build= invokes the standard Gerbil package builds and the pinned integration library's
=gerbil-rs-stage-program= / program archive API. integration library observations are forwarded
to Cargo dependency directives; ASCENT retains no parallel input index or
archive cache. Cargo consumes the integration library's link directives directly.

Optional isolated owners consume =gerbil-rs-stage-load-closure=,
=ModuleClosure=, =stage_module_closure= and integration library verified publication. Those are
the integration library's existing formats and operations, not a new ASCENT manifest schema.
There is no recursive traversal of the installed library, generation guessing,
flattening of application/integration library trees, or raw-source loader compatibility shim.
The existing application owner still retains its verified integration library package lease.

The native borrowed-static-input extent remains the existing Yuanxu API. It
provides temporary compiler write ownership for read-only dependency inputs;
it does not select binary targets or maintain a resource directory catalogue.

* Owner purpose and timeout diagnosis

An independent owner is an optional same-process Scheme VM and its sole entering
thread. Separate VM heaps and module state permit concurrent callers without
sharing Scheme objects. They also incur separate VM, GC and fixed source-context
initialization. This is not process fault isolation. Rule evaluation, Session
branching and provenance reuse do not require a separate VM per branch. The
default linked =Runtime= and the optional =InstancePool= are distinct consumers;
no accepted throughput advantage currently justifies promoting the latter.

The retained =native-owner-load-path.json= records the inspected native graph:
495 logical modules, including 236 deferred modules; the load closure contains
758 native =.o1= parts and 267 =.ssi= files, with no Scheme carriers. For example,
=std/os/fcntl~1= is a deferred linked unit and its native dynamic part appears in
the sampled owner's loaded images. These are package and graph counts, not a
count of modules loaded by the failed request.

The integration library program stub installs a scoped linked-metadata loader. The observed
dynamic loads show that the current integration does not avoid the expensive
native loading path for all of that metadata. The subsequent binding experiment
below establishes a specific incompatibility with the installed native loader;
no deadlock is established.
The inspected public integration library package copy API does not materialize the logical
aliases of coalesced module bundles. Its private owner implementation does.
Duplicating that implementation in ASCENT would reinstate the removed resource
manager; enabling a Python owner backend is outside this task. Neither is used
as a workaround, and no upstream files have been changed.

The existing opt-in =ASCENT_PROCESS_TRACE= now separates package capture or
verification, native VM setup, and source-context binding. It preserves the
original error values and both original 60-second waits; no metadata work is
moved to the first request. The exact lifecycle source binding and owner
admission theorems passed the locked =OwnerAdmission.lean= guard after this
change. Phase timing is diagnostic evidence, not a matched performance result.

* Confirmed ordinary-global versus primitive-binding incompatibility

The subsequent diagnostic used the unchanged native timeout and failed again:
package capture 2.178183 seconds, VM setup 1.379737 seconds, source-context bind
60.005179 seconds. The test reported 0 passed, 1 failed, 1 filtered out in 66.08
seconds. See =instance-loader-bindings.raw.log=. The temporary read-only binding
observation is retained in =instance-loader-bindings.hybrid.ss=, then removed
from the application. The final application source again matches the previously
checked =OwnerAdmission.lean= source literal; no loader replacement was added.

The causal evidence is narrower and stronger than a timing inference:

- The pinned integration library's =program-register-builtins!= installs an ordinary global
  =load= closure. Its linked-metadata branch calls =##load-module= instead of
  opening a native carrier file when the scoped module identity is active.
- The generated integration library program C installs that closure with =___SET_GLO=.
- The installed Gerbil =gerbil__runtime__loader.c= calls =___PRM_load= via
  =___JUMPPRM= inside =__load-module=. Its source declares =standard-bindings=.
  This call does not read the ordinary =load= global modified by the integration library stub.
- The isolated =native-loader-probe.ss= changes that ordinary global in its
  own diagnostic process only. A direct global call reaches the hook once.
  Native =load-module= then executes the carrier again and registers the module,
  while the hook count remains one. The two =NATIVE-CARRIER-EXECUTED= markers
  exclude a skipped or cached carrier as the explanation. This is a reproduced
  incompatibility, not an owner-runtime acceptance or a performance sample.
- Native expansion and interpreter compilation of =(load-module "probe")=
  both retain the =load-module= reference. An alleged rewrite of that expression
  to =__load-module= is not supported by those observations.

Reproduction uses the installed native entry only:

#+begin_src sh
gxi -:debug=q .data/ascent-native-owner-20261101/native-loader-probe.ss
#+end_src

=loader-binding-cause.json= binds the probe, inspected installed loader C, integration library
adapter, generated program C and temporary diagnostic application source by
SHA256. The probe is diagnostic data; it is not loaded by the Library, build
entry, runtime owner or package test inventory. The pinned integration library checkout has no
tracked source diff.

The currently inspected public integration library program API exposes no loader-binding policy
or alternate linked-metadata initialization entry. It reuses installed system
objects, including this native loader. Its public resource coalescing and copy
APIs do not repair the binding incompatibility. Copying loader logic, patching
primitive cells, rewriting the generated integration library stub or restoring the source-loader
shim in ASCENT would introduce an application workaround rather than use a
supported native consumption boundary; none was done. An admissible runtime fix
has therefore NOT been implemented under the current no-upstream-change and
no-compatibility-layer constraints. Independent owners remain optional and
unaccepted. The three-arm study has not run; its budgets, gates and disabled
default materialization remain unchanged.

* Standalone binding reproduction

This reproduction needs only the installed Gerbil binary. It neither builds nor
loads ASCENT or the Rust integration library. The global replacement exists only inside
this short-lived diagnostic process; it is not an application fix.

#+begin_src sh
probe_dir=$(mktemp -d)
trap 'rm -rf "$probe_dir"' EXIT
printf '(displayln "CARRIER-EXECUTED")\n' > "$probe_dir/carrier.scm"
PROBE_DIR="$probe_dir" gxi -:debug=q -e '
  (import :gerbil/runtime/loader)
  (def calls 0)
  (def variable (##make-global-var (quote load)))
  (def original (##global-var-ref variable))
  (set! load (lambda args
               (set! calls (+ calls 1))
               (apply original args)))
  (add-load-path! (getenv "PROBE_DIR"))
  ((##global-var-ref variable)
   (path-expand "carrier.scm" (getenv "PROBE_DIR")))
  (displayln "DIRECT-GLOBAL-HOOK-CALLS " calls)
  (load-module "carrier")
  (displayln "AFTER-NATIVE-MODULE-LOAD-HOOK-CALLS " calls)
  (unless (= calls 1) (error "different native binding behavior" calls))'
#+end_src

On the recorded toolchain the carrier executes twice while both hook counts
are one. This distinguishes an actual native-load bypass from a cached or
skipped file. The native installed-loader C and generated integration library-stub C evidence
above then identifies the primitive-versus-ordinary binding mismatch. Other
toolchains may differ; the diagnostic must not be treated as their result.

* Later compiled-call evidence: checked versus unchecked entries

A subsequent integration-library investigation on the installed 1cfb032
compiler adds a distinct observation. The earlier expansion/interpreter probe
retained load-module; it did not establish what the optimizing native compiler
emits. A compiled runtime helper with a literal string argument emitted
__load-module, while its assignment still updated the checked load-module
binding. Its generated C called the unchecked global directly. Reassigning the
checked procedure therefore did not observe that optimized call.

This is separate from the previously recorded primitive-load versus ordinary
load incompatibility. Neither observation authorizes changing primitive cells
or adding a source-loader workaround to ASCENT. Instrumentation at a checked
entry cannot be treated as a complete account of native execution after
contract specialization. The integration library's current candidate instead
uses ordinary compiled-library loading and observes the native module resolver
through its existing extension point. That candidate and its tests are owned
by the integration library; ASCENT consumption remains a separate pending gate.
