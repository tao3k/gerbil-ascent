#+title: Compiler layout and source-bound preparation costs
#+date: 2026-10-19

* Problem and scope

The remaining 23--35 seconds of source-Suite context loading is not the
whole cold preparation problem. These measurements keep three build cores,
the 240-second source-runtime limit, twelve Rust binding test threads, and
all existing semantic, cancellation, resource, provenance and performance
gates. The immutable released Gerbil 1cfb032 / Gambit ea114fc SDK is unchanged.
No application or reference workload is modified.

* Existing cost evidence

The d151 instrumented candidate cold preparation recorded 671.042620 seconds
of inclusive GSC CPU. Native C helpers account for 562.601045 seconds within
that total; they must not be added again. The remaining 108.441575 seconds
includes the Scheme compiler, observer and other overhead, not just expansion.

| Native helper class | Calls | Input bytes | CPU seconds |
|---------------------+-------+-------------+-------------|
| Runtime C units     |   253 |   146925922 |  409.511529 |
| Loader C units      |   253 |     2041631 |   89.209884 |
| Phase/meta C units  |    83 |    12322980 |   63.879632 |

The SDK deliberately emits distinct runtime, loader and phase units. This
is not evidence that the same object was compiled repeatedly. Across 173
nonoverlapping outer test imports, GC accounts for approximately one quarter
to one third of CPU, not all context loading. Nested imports are excluded
from this sum. The source-work decoder rejects overlapping root intervals
and mixed clocks.

* Supported SDK layout policy

The existing gambit.h supports ___SINGLE_HOST_LIMIT. The declared compiler
option sets it to 512: small units retain their existing C function layout;
large units use multiple C functions. This has no relation to VM concurrency.
The C optimization level is unchanged. The production PackageSpec, test make
specifications and Rust build graph consume the same declared option through
the existing ASP normalizer. SDK loader/meta paths reset compiler options;
no claim is made that this setting affects every helper.

On one identical 2,936,432-byte captured UF C input, the unchanged native SDK
helper used 5.028917 CPU seconds with limit zero and 3.684581 with limit 512
(26.7 percent less). This is a local compiler experiment, not an end-to-end
speedup claim. Final-record declarations did not reduce the toy generated
input and were rejected. GCC parsing was only about 10 percent of runtime
unit CPU, so precompiled headers were not selected as the primary remedy.

Native make checks timestamps rather than changed compiler options. A scoped
receipt binds SDK home, source root and declared options. A mismatch removes
installed test-owned outputs, including unrequested old Suites, before native
make. Production carriers remain under the existing producer admission.
The receipt is written only after successful make and unchanged source
inventory. It is not a cached build-success or source-graph verdict.

* Cumulative allocation and source correspondence

Native GCC SARIF time reports supply the exact integer TOTAL ggc_mem counter,
the cumulative allocation of GCC's garbage-collected allocator. The decoder
requires one successful GNU C invocation and the matching actual C input;
the observer retains and hashes the raw report and input. Nested pass counters
are not added. Coverage requires every expected C helper, no failed helper,
no changed input and no report error. Missing or partial coverage remains
unobserved. These are GGC allocations only, excluding other GCC allocations
and Scheme VM allocations.

CompilerCost.lean renders the actual compiler declaration, option-receipt
reader/writer, stale-output selection, compiler-input roles, unique-source attribution, TOTAL guard and coverage guard. Formal
CI compares these regions byte for byte and renders CompilerPolicy.qnt from
Lean. CompilerCost.qnt checks successful profile publication, invalidation
and counter scope with fifteen independent fault controls. Native tests exercise
actual supported SDK code generation, tail calls, values, one processor per
VM, option-receipt rejection and native SARIF attribution.

The full SARIF decoder, Scheme reader, SDK compiler, allocator implementation
and filesystem traversal remain external implementation premises. Generated
guards and bounded models do not prove those complete implementations.
Scheme endpoint occupancy counters still do not establish cumulative VM
allocation. The old negative-counter and historical-regression gates remain
strict; native GCC evidence does not replace or waive them.

* Baseline drift protocol

A fixed SDK-generated C input is compiled after each complete ABBA control.
Its content hash, CPU/wall time, faults, context switches and cumulative GGC
allocation are retained outside application phase timings. This provides a
matched compiler-work-rate diagnostic without dropping the first control,
normalizing application times or warming an application prefix. A drift in
that calibration does not identify a particular host or filesystem cause.
Both source hashes must remain current. Instrumented work and uninstrumented
wall-time experiments run independently, with foreign-build audits.

* Validation status

Local native/compiler and preparation tests, full Lean/Quint verification,
exact-head CI and independent ABBA measurements are recorded separately in
the PR acceptance section. Until the new controls complete, the local C
micro-experiment is the only measured compiler-layout benefit. Reduced
context counts and a green CI are not closure of cold expansion or real
cumulative Scheme allocation.

* Containing-source cost attribution

Every native C helper now retains its actual C inputs, containing GSC observer,
exclusive CPU, retained GCC report and exact GGC total. A generated Scheme
input is attributed only when its normalized path matches the C input inside
one unique containing GSC observation. Cross-parent, missing and ambiguous
matches remain unattributed; duplicate containing process identities reject
the observation. Costs are not added to their inclusive parent again.
The path/confinement guard is generated from Lean, and Quint includes separate
cross-parent and ambiguous-input fault controls. These guards do not prove
that the SDK compiler implements Scheme semantics, establish original DSL to
expanded-Scheme equivalence, or observe every Scheme allocator. Those remain
explicit gaps alongside cold expansion and baseline/runtime variability.
