#+title: Operator lexical scope compilation qualification

=reference.ss= freezes =program/operator.ss= at

are qualified so it can coexist with the production implementation.

Run =just performance-operator-scope=. The existing project library and SDK
must be prepared first; this entry builds project modules, not the SDK.
Scenario, library and receipt paths are explicit Scheme arguments. All
executables, raw pairs and logs belong under ignored =.cache/ascent/=.

=benchmark.ss= was generated with the public ASP
=make-benchmark-fixture= API. It owns sample count, baseline identity,
scenario sizes and the original relative thresholds. The runner checks
=benchmark-fixture-contract-pass?= and delegates the series to
=benchmark-run/result=; the saved receipt includes its standard p50/p95,
timing source and runtime memory observations under =asp-receipt=.

Each ASP sample is one alternating old/new pair with semantic checks.
Its wall-clock p95 includes the pair, heap preconditions and those checks;
it is diagnostic, separate from the compile-only relative gate.
The narrow Gambit CPU/cumulative-allocation span remains necessary: ASP's
heap observations are not the same counter as total allocated bytes.

Each side constructs its own descriptors before timing. Each timed call
includes validation, detached rows, lexical analysis, lowering and program
construction. Fifty alternating pairs compare CPU and allocation. Outside
the timed region, normalized emitted relation/rule topology must match,
and each program must solve natively to the independent expected row =((7))=.

The scaling scenario has 19 shared union levels and one bound parameter.
It retains the gate fixed before the first 18-level sample: 20% less median CPU,
35% less allocation and 35/50 CPU wins. The one-level control allows
5% + 20 us CPU overhead and 2 KiB
allocation overhead. Neither gate measures solver speed or wall time.

The initial 14-level =diamond= scenario remains callable. It failed the
same 80% gate: CPU 49,251 -> 47,165 us and allocation 101,052,176 ->
94,933,872 bytes. Its 49/50 wins do not establish a substantial complete
compile gain. At this size object construction dominates the saved lexical
analysis. At 18 levels, =shared-diamond= improved CPU from 74,805 to
39,461 us (50/50 wins) and allocation from 169,848,416 to 119,963,392
bytes. The 29.4% allocation reduction failed its 35% gate; that scenario
remains callable with the same gate. The 19-level scaling run retains
these thresholds rather than weakening the allocation requirement.

The 22-level =deep-diamond= experiment could not produce pairs:
the frozen baseline raised stack overflow in lowering. It remains callable
with the original 80% gate. Do not report a percentage speedup for that
experiment. The production unit test independently compiles and solves
this 22-level graph, also checking escaped bindings and later pointer cycles.
