#+title: Built-in Set rule output admission

The evaluator recognizes the exact built-in Set storage Provider and admits
its head row directly. Its extension function is exactly =(list row)=;
the candidate avoids that temporary list and the callback/iteration overhead.
Both field validations, membership checks, row order and global budgets remain
in their original order. Custom Provider extensions and lattice joins retain
their existing paths.

The compiled frozen evaluator is committed =0330692:program/evaluate.ss=,
with only the two export names changed and relative imports relocated. Both
implementations share identical current dependencies and compiler options.
=just set-emit-benchmark= records source hashes before building in a private
library directory. This is a whole-solve comparison, including construction,
rule execution and result snapshots, not just an admission kernel.

The exploratory closure-based implementation did not meet the recursive-chain
1000-pair win gate. Its raw log and samples are retained as =exploratory-chain*=.
An initial dense-output golden mistakenly assumed arrival order; native
behavior emits the reversed first-admission order within one round. That
fixture error is retained in =exploratory-golden-error.log= and corrected for
both frozen and candidate evaluators.

The pre-shared-check candidate's single-solve samples are retained in =single-solve*=.
All medians improve, but dense unique/duplicate paired wins are only 648/760
of 1000, below the >=900 gate. They do not establish a qualified single-call
latency gain. Dense output admission below instead uses samples averaging ten
complete solves to amortize GC phase. It measures sustained solve throughput;
it does not supersede the failed single-solve evidence or the original SS
latency budgets. Each of 1000 alternating pairs checks exact ordered goldens
outside the timer, after 20 warmups. Dense batches still require >=900 wins;
recursive chains 16/256/1024 remain controls with median non-regression. The
16-chain control averages 20 solves because its ~17 us time is near clock
quantization and dispatch noise. Every individual solve retains the original
bounds, and the runtime heap remains 1 GiB.

The source associated with the timing samples is retained as
=candidate-before-shared-check.ss=. Those timing attempts were rejected. The
shipped implementation factors admission validation and membership updates into
one per-round function, retaining the direct built-in path. It passes the
unchanged module-size policy; both earlier policy errors remain in qualification
logs. No timing win is claimed for the final source.

Final-source allocation comparison
---------------------------------

=just set-emit-allocation= observes Gambit =##process-statistics= slot 7,
the cumulative allocated-byte counter. The meaning is confirmed in Gambit's
[[https://github.com/gambit/gambit/blob/master/lib/_kernel.scm][kernel source]] and calibrated against a one-million-element vector on this
installed runtime in =counter-calibration.sexp=. Slot 16 is the latest GC
allocation gauge, so the initial slot-16 probe returned misleading zero deltas.
That probe was stopped after diagnosing the metric error; its log and source
hashes are retained as =allocation-gauge-error*= and excluded from admission.
No dependency code or SS memory budget was changed.

Each of 1000 alternating pairs measures allocations during a complete solve;
ordered goldens are checked outside the observed interval. The two statistics
reads add equal instrumentation overhead on both sides. Automatic GC remains
visible through the cumulative counter. Dense output uses one solve per sample;
the tiny recursive control averages 20 solves. All controls require median
non-regression; dense output also requires >=900 strictly lower allocation
pairs. This is allocated bytes, not peak memory, retained live data or speed.
