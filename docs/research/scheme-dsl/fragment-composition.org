* Interpretation

The first-class object in the paper is a constraint set: functions may
construct and combine it, then =solve= computes its model.  This supports
placing whole-program composition in ordinary Scheme values while keeping
the rule arrow and relation atoms as the relational core.  It does not
justify hiding a changing relation read inside a host procedure.  Flix's
type and stratification checks are part of why its composition is safe;
our Scheme declaration path must offer an explicit substitute.

* Deeper result: composition carries a proof boundary
:PROPERTIES:
:CUSTOM_ID: flix-composition-boundary
:END:

The paper's examples pass constraint sets through functions and compose
them before =solve= (§2, PDF pp. 3–5).  Row-polymorphic types record
predicate names and tuple types, so the paper can reject a composed
program whose =Edge= facts are ternary but whose rules use binary
=Edge= (§2.3, PDF p. 5).  The exact Gerbil analogue would need a
combined schema check over included relations, rule arities, and field
contracts before evaluation.  A successful check of each fragment
alone is not enough.

For negation, Flix's §4.7 does more than inspect one chosen result.
Its proposed algorithm gathers constraints from the whole program,
uses a row type to restrict the possible dependency graph for an
expression, and checks that graph before runtime composition (PDF
pp. 18–20).  It is sound but conservative: it can reject programs
whose actual branches never combine into a negative cycle.  Our
=ascent-fragment= values and =(include ...)= expansion do not carry
Flix row types or this whole-program theorem.  The narrower Gerbil
claim available today is validation of the *assembled* program at
the composition boundary, followed by its dependency-strata check.
If a requirement demands assurance for every possible runtime choice
of fragments, that needs a separate static summary and proof.

The paper's composition law (union, commutativity, associativity,
idempotence) assumes pure, total constraint expressions (§3.2, PDF
p. 8).  Gerbil fragments can contain ordered source rows, user
procedures, storage providers, and resource budgets.  Equality of
mathematical rule sets therefore does not imply equal execution
order, effects, diagnostics, or partial timeout snapshots.  A
commutativity claim here must be scoped to complete *fact sets* for
compatible, pure, total fragments after successful admission.

#+NAME: flix-composition-assurance
| Boundary | Required evidence | Claim allowed |
|----------+-------------------+---------------|
| Single fragment | Local declarations and rules validate | Fragment is internally well-formed |
| Assembled program | Combined names, arities, field contracts, and strata validate | This concrete composition is admitted |
| All possible runtime compositions | Sound summaries for dynamic choices, including negative edges | Static universal assurance, not currently implemented |

The present =program/syntax.ss= validates included fragment values and
collects declarations and rules.  =program/analysis.ss= rejects duplicate
relation names, mismatched widths, and invalid field predicates in the
assembled schema.  =program/funs.ss= computes strata and rejects cycles
with strict edges.  These checks are relevant evidence for the second
row, but do not implement Flix's row-polymorphic type inference or its
all-compositions theorem.

* Expanded experiment

Test three compositions: two compatible fragments in both orders;
individually valid fragments with conflicting relation arities; and
two fragments whose combined rules create a negative cycle.  Record
assembly/admission results before running.  For pure accepted
programs, compare complete fact *sets* and then separately record
order, timeout snapshots, and resource use.  A future static summary
could be tested with a conditional choice between fragments that
cannot occur together: rejecting it may be sound but conservative,
matching the trade-off described by Flix.

* Composition experiment

Construct two pure rule fragments whose relation declarations are owned
once by the assembled program.  Compose their rules in both orders;
after admission, their complete fact sets should agree.  Repeating a
fragment with relation declarations currently creates duplicate names
and should be an admission test, not an assumed idempotence law.
Repeat with a negated edge that creates a negative cycle only after
composition: the assembled program must be rejected.  If rule order
changes complete accepted fact sets for pure total fragments, the
proposed set-like composition fails.

#+begin_src scheme
;; Pseudocode for the experiment; not a new API commitment.
(compose-fragments declarations rule-a rule-b)
(compose-fragments declarations rule-b rule-a)
#+end_src

Check relation arity and value predicates before evaluating either
composition.  Record the admission error separately from run output.
