* Reading for the proposed relation view

Datafun's monotone function is monotone with respect to the order on its
argument.  Our candidate view =f : I -> finite-set(O)= has a narrower
claim: when =f= is fixed for a source snapshot, mapping a growing input
relation =R= to the union of =f(i)= for =i in R= is monotone under set
inclusion.  It does not require =f= to be monotone in the individual
value =i=.  This is our derivation, not a theorem supplied by the paper
for Scheme procedures.

A closure that reads a mutable table, clock, or evolving relation can
produce different rows for the same =i=.  Then the apparent pointwise
view may hide a dependency or break replay after source replacement.
Datafun's separate contexts and monotone typing illustrate why an
unrestricted host call inside recursion needs an admission boundary.

* Experiment and falsifier

#+begin_src scheme
;; Proposed interface only; this is not implemented syntax.
(relation-view next (from) (to) successors)
((out y) <-- (node x) (next x y))
#+end_src

Admit one deterministic finite =successors= implementation, then attempt a
closure that mutates its output for the same =x= in one run.  The latter
must be rejected by a documented contract or isolated from fixed-point
evaluation.  Replacing the source must invalidate any retained output.
If the engine can silently reuse stale output, the proposed interface
fails its stated snapshot semantics.

* Open proof obligation

Specify how Gerbil declarations establish stability, finite emission,
and visible dependencies.  Runtime examples cannot prove these laws for
arbitrary closures.  Budget enforcement is an operational bound, not a
Datafun-style monotonicity proof.
