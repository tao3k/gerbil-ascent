* Ordinary directory tests and memory policy (2026-10-08)

Ordinary qualification Cases use upstream =std/test= directly. Thirty-seven
Suite source files previously wrapped semantic checks in POO Flow's testing
Case policy. Its default =heap-limit-bytes= is 1 GiB and measures the entire
process heap, including every module imported by directory discovery. Merely
setting Gambit's heap cap to 2 GiB therefore leaves a contradictory Case
policy. The unaligned 2 GiB probe produced =PooFlowDebugMemoryAnomaly= errors
and did not finish within its 120-second bound.

Two ordinary Suite profiles also enabled =collect-before-sample?= while
inheriting a 10-millisecond sampling interval. The watchdog calls =##gc= before
such samples. A directory process retaining all expanded modules makes these
whole-heap collections materially different from a focused module test.
The separate 1 GiB =gxi= GC diagnostic observed approximately 716 MiB live and
repeated collections of approximately 190--230 milliseconds; that diagnostic
is not a matched timing estimate for the stock =gerbil test= entry.

The generic policy wrappers and local semantic Case profiles have been removed.
Case descriptions, bodies, fixtures and assertions remain intact. The dedicated
observability Suite still verifies policy rejection and bounded execution.
Ordinary Cases no longer claim those removed per-Case heap or duration quotas;
the process heap cap, command deadline, failed-Case detection and final verdict
checks remain. Runtime resource rejection is tested explicitly rather than
injected into unrelated application code by a Case sampler.

=just test [heap]= now invokes the standard Gerbil directory entry once.
=just test-file <path> [heap]= retains focused execution. The heap parameter
controls the source-test process; native entry and compiler qualification keep
their separate existing limits. No additional test runner or supervisor is used.

The source recipe also honors the caller's existing dependency load-path order
before appending the checkout. A resolver probe confirmed that source-first
ordering selects =program/evaluate.ss=, while the prepared-library-first order
selects =gerbil-ascent/program/evaluate.ssi=. CI prepares the content-bound
native library before supplying that path. Explicit Suite file paths continue
to exercise Suite source. Supplying an arbitrary stale library is not source
qualification; the prepared dependency snapshot remains part of the evidence.

Three relation-view cost Cases have moved intact from the semantic Suite to
=t/performance/ascent-relation-view-performance-test.ss=. Their 12 matched
pairs, explicit GC boundaries, allocation/live sampling and truth checks are
preserved. Shared construction and row-order helpers now reside in the existing
qualification fixture namespace. Complete native qualification includes the new
performance module and prepares its common fixture/reference dependencies before
consumer compilation. Its roster is now 95 modules and 852 Cases; the ordinary
source directory contains 89 modules and 843 Cases. This separation changes the
ordinary workload and cannot support a same-workload percentage speedup claim.

The source-first experiments after removing the generic policy wrappers still
failed to finish within 120 seconds at 2 GiB or 180 seconds at 3 GiB, despite
reporting no policy errors. Correcting load-path order alone also failed to
finish the benchmark-bearing directory within 120 seconds. Capacity, dependency
loading and benchmark placement are separate issues; none of these failed
experiments is counted as a qualification pass.

With prepared dependencies first, the complete standard directory invocation
passed all 89 modules and 843 Cases in one process at 2 GiB: exit 0,
=HARNESS-OK=, final =OK=, 106.61 seconds (102.86 user, 2.37 system). The original
120-second deadline remained unchanged. Dedicated memory/duration rejection
Cases were included. This is a prepared-dependency correctness receipt, not a
cold-build result or proof of optimal memory capacity.

Complete native qualification also passed all 95 modules and 852 Cases. The
formal command was =just test-native-suite= with its unchanged =auto= default.
ASP's existing capacity projection selected 12, matching the current host CPU
count and configured capacity. The real lifecycle trace reached 12 active
workers, completed all 95 modules and drained to zero active workers. Exit was
0, with no failed Cases. This prepared-library/entry-cache run took 89.23 seconds
(127.97 user, 8.00 system). The preceding fixed-four-worker preparation run was
an experimental control, not the formal capacity selection or a hard limit.
These different preparation workloads do not establish a concurrency speedup.

The earlier process-pool measurements below are historical observations from
the preceding revision. They do not describe the current ordinary recipe and

* Complete test preparation and bounded execution (2026-10-08)

The installed Gerbil =gxtest= implementation and
[[https://cons.io/reference/dev/test.html][official testing documentation]] support one invocation over files or a
directory. They do not require one operating-system process per source module.
The previous =just test= recipe nevertheless launched 89 module invocations
serially. A directory-wide source probe under the unchanged 1 GiB heap failed
with heap overflow after 20.89 seconds; it also reported a failed Check before
the overflow. This probe is rejected, not a qualification pass.

The preceding ordinary recipe accepted a worker capacity, used the existing native
capacity projection for =auto=, and overlapped standard =gerbil test= module
invocations through =xargs=. Module expansion remains isolated; each invocation
retains its own Case/output/exit gates and the original 120-second deadline.
The full source inventory passed: 89 modules, 846 Cases, exit 0, 113.93 seconds
with four workers. This is an observed complete run, not a matched claim of a
specific speedup over the user's ten-minute report. CI runs this complete source
inventory after native preparation supplies its compiled reference dependencies.

Native preparation previously allowed its executable-backed library cache hit
only for one requested module. It now also admits complete pools, binding the
ordered entire roster in the existing receipt key. Reordering, adding, removing
or replacing requested modules rejects admission. Each entry mode retains its
last admitted executable; switching rosters deliberately misses rather than
providing an artifact store for every prior roster. An empty roster raises a typed
Error. Source, compiled dependency, environment, toolchain, generated entry and
binary content checks remain in force. Test verdicts are never cached.

On a preparation miss, production and reference dependency layers finish before
Suite consumers start. Existing actors schedule bounded independent compiler
processes. Each child has a private =mktemp= specification removed on success or
failure, a 1 GiB heap and one compiler core; this avoids shared-specification
races and nested core oversubscription. Failed consumers stop pending admission
and active workers drain through the existing actor lifecycle.

The complete native inventory comprises 89 qualification and five performance
modules. Its first qualification passed all 94 modules and 852 Cases in 411.62
seconds. Compiler lifecycle output verified 94 consumer completions, a maximum
of four active consumers and zero consumers left active. The identical repeat
passed all 94 modules and 852 Cases in 67.18 seconds, reporting both library and
entry cache hits with zero compilation/link invocations. Cold and hot runs are
different workloads; these numbers do not establish a cold-build speedup.
Subsequent recipe changes intentionally invalidate the old content-bound entry;
CI must qualify the submitted complete source snapshot independently.

The frozen compiler comparison in gerbil-bazel retains responsibility for the
Darwin C/object regeneration hypothesis. Its baseline must not incorporate
these ASCENT orchestration changes or attribute their benefit to Gambit.

** Use case to consumer mapping

Read the pinned [[https://github.com/tao3k/lean-poo/blob/247d1d6094b6af1bb873f69564b271bc978730ed/docs/use-case.md][PO use case]],
[[https://github.com/tao3k/lean-poo/blob/247d1d6094b6af1bb873f69564b271bc978730ed/docs/usage.org][usage guide]] and
[[https://github.com/tao3k/lean-poo/blob/247d1d6094b6af1bb873f69564b271bc978730ed/docs/reusable-contracts.org][reusable contracts]] together.
The primary PO path declares typed behavior, composes declarations through
C4, then evaluates slots through a shared lazy instance. Proof objects are
an additional capability for consumers carrying obligations across changes.
ASCENT currently consumes that proof capability for source/result cuts.

| Workflow | LeanPoo API | ASCENT responsibility |
|----------+-------------+-----------------------|
| Declare correctness once | =Obligation=, =ProofObject=, =Certificate= | =resultObligation= states derive/observed equality; RuleBodyFrame supplies semantic locality |
| Apply ordered source edits | =Patch.setMany=, =Patch.composeAll= | Admit the actual source cut and preserve last-write order |
| Carry an unaffected proof | =reuse=, =unaffected_setMany_iff= | Prove dependency/touched-key disjointness from the compiled rule closure |
| Select affected obligations | =pending=, =mem_pending_iff= | Revalidate touched positive, negative and aggregate dependencies |
| Publish a complete certificate | =closePending= | Discharge every selected old or newly added obligation |
| Relate staged and batched edits | =append_composeAll=, =unaffected_composeAll_iff= | Check every constituent footprint, including repeated writes |

The compiled =stagedReuse= use case in AscentProofTests applies two edits
to an unrelated source and carries the original certificate into the exact
stepwise result through the producer's composition laws. A control writes a
dependency and then restores its original value: it remains pending. Final
value equality alone cannot authorize proof reuse.

** New capability boundary

The updated reusable-contract modules also expose typed capability families,
prepared consumer caches, indexed registry transactions, narrow/public views
and certified solver transport. =applyTransactionCached= publishes the full
registry transaction and distinguishes =reused= from =fresh=; fresh data still
requires an analytic certificate. =CertifiedTransformation= requires supplied
forward validity and reverse witness soundness; =pullSolver= transports an
already admitted solver's data and proof. These are concrete public APIs,
not automatic dependency discovery or a solver generator.

ASCENT's current source state is a dependent key/value function, not a C4
provider registry. Its native planner, physical index and publication protocol
still need their own source-bound qualification. The existing Proof APIs
remain compatible at this revision; adopting the new registry workflow would
require an explicit provider/context mapping and a refinement to this source
cut. This synchronization records the usable boundary and qualifies the
current consumer against the new producer without claiming that mapping.

Qualification: =direnv exec . just check-lean-proofs= completes with exit 0
and 83 Lake jobs. =stagedReuse= reports only =propext= and =Quot.sound=;
the restoration control compiles as a kernel-checked pending-membership proof.
This gate qualifies the updated Lean consumer; it supplies no new native
performance or publication receipt.

** Existing consumer migration: prepare reads independently of the cut

=FunctionalDependency.lean= now uses the producer's context adaptation workflow
in its existing implementation. =provider= selects source-reading functions
whose context is the complete typed source cut. =Program.prepare= depends only
on a target's checklist. =Program.step= adapts that prepared tuple to the
current cut with =Requirements.reindex= and feeds the existing rule evaluator.
Previously each provider captured one source cut before preparation.

=Program.step_eq_prepared_cut= proves the migrated evaluator equals its
previous per-cut behavior for every source/checklist. =Program.prepare_at=
applies upstream =prepare_reindex= to prove the adapted
tuple equals independent preparation at the exact cut, including the complete
success/error outcome. =Program.local= combines this law with =prepare_congr=;
=SourceUpdateFrame.completed_reuse= and the downstream RuleBodyFrame proof
continue to use the same locality contract. No separate solver-route module
is part of this migration.

The existing AscentProofTests retain one checklist with heterogeneous Nat/Bool
values and a repeated Nat key, then adapt that same tuple to two source cuts.
They check current values and duplicate request order, while the existing
self-read and completed-frame fixtures qualify the changed consumer. Preparation
is independent of the cut; these Lean contracts do not demonstrate a native
cache or a runtime speedup. The native Scheme implementation has not changed.

Qualification: =direnv exec . just check-lean-proofs= succeeds with exit 0
and 84 Lake jobs. The preparation correspondence and evaluator equivalence
report only =propext=; the existing completed-frame theorem retains its
standard-only axiom report. The earlier solver-route files and imports have
been removed because they did not migrate the existing consumer.
