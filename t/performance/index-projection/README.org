#+title: Physical index batch insertion and projection

* Ownership and source study

The production change belongs to =table/funs.ss=. Gerbil's
=compiler/optimize-call.ss:89-131= distinguishes immutable references and
quoted arguments from expressions requiring temporaries. Its
=runtime/table.ss:440-464= implements synchronous =hash-update!= with one
hash/probe path. These are concrete expression and ownership patterns, not
an assumption that the compiler automatically moves a captured branch.

The batch selects its entire ordered/arbitrary projection loop once. Ordered
columns become forward cursor distances once per call. A batch-owned row slot
and one updater replace each row's =hash-get= followed by =hash-put!= without
allocating a captured updater for every row. Bucket insertion creates a fresh
spine, preserving previously returned bucket lists. Arbitrary/repeated columns
retain direct projection. Caller columns are neither mutated nor cached.

* Measurement and admission

Fixture construction precedes timing. Each leg includes physical index build,
extension and eight key lookups (four for the small control). Alternating leg
order and a collection before each leg limit ordering/GC bias. Both results
must equal an independent direct projection/filter oracle outside the inner
timed spans. Wide/compact/fallback use four repetitions per leg; small uses 64.

The wide gate requires CPU <= 80% of baseline, at least 35/50 paired CPU wins,
and <= 4096 extra allocated bytes per lifecycle. Controls allow at most 5%
CPU plus 20 microseconds and 4096 extra bytes (1024 for small). These gates
were fixed before the final optimization. Standard paired wall p95 remains
diagnostic. This benchmark does not measure whole solver speed.
