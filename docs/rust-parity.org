#+TITLE: Rust Ascent to Gerbil parity contract
#+DATE: 2026-09-26
#+STATUS: incomplete implementation matrix

* Authority and completion rule

The first target is behavioral parity with the pinned =ascent 0.8.0= oracle,
interpreted through Scheme and Gerbil modules. The [[https://s-arash.github.io/ascent/cc22main-p95-seamless-deductive-inference-via-macros.pdf][CC 2022 paper]],
[[https://kmicinski.com/assets/byods.pdf][BYODS paper]], and [[https://github.com/s-arash/ascent][Rust implementation]] define the baseline.
Rust-specific surface syntax and ownership rules need equivalent Scheme APIs
and macro behavior; copying Rust syntax is not a requirement. Each row closes
only with a matching Rust fixture, Scheme result comparison, invalid-program
test where relevant, and a measured performance receipt. Until then, this
repository is a partial implementation, and Agent extensions are research
proposals rather than core parity claims.

* POO Flow programming style in the Scheme implementation

ASCENT declarations are POO values admitted by Core =define-type=
contracts. Clause planning has one independently extensible receiver family,
so its public dispatch is the slot generic =gerbil-ascent-clause-plan=.
Relation indexing is a separate one-receiver Provider family with slot
generics for build and lookup. A downstream index Provider extends
=gerbil-ascent-hash-index-provider= with native =.o= inheritance and overrides
the relevant method slots; the alist qualification fixture exercises this
surface. Public Provider construction does not require a positional pair of
callback functions.

Index construction, equivalence closure and rule evaluation remain named Scheme algorithms. The
tagged vectors inside the evaluator are private lowered plans, not a second
public declaration language. There is currently no independently growing
Provider-by-Profile crossing, so adding CLOS methods here would not satisfy
the POO Flow two-axis rule. The current BYODS storage Provider has a separate
semantic contract and selected Rust parity fixtures; its broader merge and
scale behavior remain open. Pure transitive algorithms live in
=table/funs.ss=; =table/eqrel.ss= owns an evaluation-local component index;
=table/trrel.ss= owns evaluation-local predecessor and successor indexes;
=table/storage.ss= owns the POO storage Provider contract and method selection.
The Provider's =.make-state= slot creates one private state per relation and
evaluation. Its =.extend-rows= slot receives that state, the current rows,
the incoming row and the remaining fact budget. This separation allows Gerbil
and its Standard Library to determine the implementation instead of copying
Rust's data-structure layout.
The evaluator resolves each storage Provider method slot once when it
initializes a relation, then invokes the selected Scheme function in the row
loop. This preserves the public POO extension point without repeated slot
dispatch for every fact.
Input budgets count declared source rows; total output budgets count
materialized source rows after BYODS expansion plus derived rows. A
qualification case checks that a two-edge =eqrel= source cannot materialize
nine rows and then derive nine more under a twelve-row output limit.
Dependency stratification, delta-position planning, lattice row operations
and rule binding live in =program/funs.ss= as named Scheme functions. The
evaluator retains session-local fact buffers, pending deltas and rule
execution state. Immutable lowered rules and strata are cached by the
identity of the declared POO program with weak keys; cache access is
serialized, while every evaluation builds separate fact buffers, indexes,
BYODS state and budgets. POO refinement creates a new program identity and
therefore receives its own analysis. This is Scheme planning inside the
evaluator, not a separate source or runtime language. Its public
=GerbilAscentSessionContract= exposes
=.append-source!= and =.run= procedures. =gerbil-ascent-open-session= creates
one session; the one-shot API executes that session once. Results contain
stable row snapshots. A second run without new materialized rows reuses its
result, while positive relation-atom rules consume appended source deltas.

The current Rust oracle in =rust/ascent-oracle/= covers positive binary
closure, guarded filter/copy/join, shortest source support, and selected
arbitrary-column rules, =if= guards, =let= bindings, =for= generators, stratified negation, selected aggregation and shortest-path lattice joins across
source snapshots. Scheme generators consume Gerbil Standard Library iterables
and name their input variables explicitly. These fixtures do
not close the rows above. =candidate/= and
=interface/= hold existing experimental projections; their MRR or Agent use
cannot substitute for Rust feature parity.
The derived-aggregation differential lets =path= reach its recursive fixed
point before =reach-count= counts paths for selected roots in the next stratum.
Empty, chain, cycle and duplicate-edge inputs match Rust, including a zero
count for a root without paths. This is aggregation over a recursive input,
not a recursive aggregate dependency: pinned =ascent_macro 0.8.0=
rejects a cycle through an aggregate with its
="use of aggregated relation ... cannot be stratified"= diagnostic in
=ascent_mir.rs=, and the Scheme qualification rejects the same dependency.
The standard =ascent-derived-aggregate= SS scenario evaluates the declared
three-edge cycle and isolated root for 20 samples under the unchanged 1 ms
budget used by the other small recursive scenarios. It checks all nine path
facts and four counts outside the timed region. Its Linux performance receipt
must be read from the exact pinned POO Flow CI head.
The positive binary differential now includes an empty source, a self-loop,
duplicate edges, disconnected cycles and overlapping paths. Both the binary
fast path and generic rule path compare their complete sorted closure with
the pinned Rust oracle for each snapshot. These finite graphs check boundary
and deduplication behavior; they do not establish arbitrary-graph parity.
The positive generic fixture also compares =dependent(x,y)= from =node(x)=
and the Standard Library =in-range= iterator bounded by =x=. The corresponding
Rust =Range= yields zero, one, or two values for the three source nodes. The
same fixture exercises a vector-backed generator with two bound output
variables and the original list-backed generator. Tuple values may be lists
or vectors; duplicate output names and wrong tuple widths reject. All remain
within the unchanged 32-fact derived budget.
The nullary-gate fixture checks absent and present zero-column facts with
boolean and string data, duplicate input rows, and empty strings against
the pinned Rust Ascent 0.8.0 oracle. The macro's generated Rust code emits
an unused local binding for this nullary declaration; the test suppresses
that warning only for this fixture.
The mutual-recursion fixture declares its seed rule after the two recursive
rules and includes a directed cycle. One recursive rule has two heads:
=path1(x,z)= and =witness(z)=. All three derived relations match Rust after
deduplication for an empty source, a self-loop, a cycle, reversed source
order, duplicate edges, a branching graph with a cycle, and a finite chain.
This is evidence for one SCC shape, not a general termination proof.
The standard =ascent-mutual-recursive-heads= SS scenario measures 20
evaluations of a predeclared three-edge cyclic program with a 1 ms p95
ceiling. It checks all nine rows in each path relation and all three unary
witnesses outside the timed region. The [[https://github.com/tao3k/poo-flow/actions/runs/36287894639/job/108532047947][POO Flow Ubuntu native job]] at
POO Flow =6598403= and ASCENT =be30fef= measured 544.178 us p95 and passed
the unchanged ceiling. This is one selected recursive multi-head shape and
does not close the wider performance or termination corpus.
The repeated-run oracle uses one Rust program for an initial edge, a second
edge, an unchanged run, a duplicate source edge, and a closing cycle. The
multi-head SCC fixture additionally compares retained Scheme and Rust sessions
after every phase, including a two-edge branching append and another back
edge. It also checks fresh Scheme snapshots at every Rust phase. Pinned Ascent
0.8.0 calls
=update_indices_priv= at the start of =run=; its generated
=compile_update_indices_function_body= iterates every row in each relation.
Therefore Rust's retained program object is not evidence of an O(delta)
update. Scheme now has a public retained session for positive atom-only
source additions; the reachability and grouped BYODS fixtures compare its
results with fresh evaluations while checking earlier snapshots stay stable.
The mutually recursive multi-head fixture also retains one Scheme session
through an initial edge, a second edge, an unchanged run, a duplicate edge
and a closing cycle. Scheme checks =path0=, =path1= and =witness= against fresh
evaluation after each changed prefix and checks that earlier snapshots stay
stable. The Rust oracle repeats =run()= on one program through the same
sequence and compares each result with both retained and fresh Scheme output.
These checks cover one wider positive update shape, not deletion or
nonmonotone incremental semantics. The Rust oracle package runs the ASP Rust
package policy as a dedicated test. Its differential cases live in
responsibility-specific integration modules mounted by a thin Cargo target.
The standard SS scenario =ascent-session-update= prepares 20 sessions outside
the timed region, then times one source append and recursive closure per
session. It checks all 20 results and passed the [[https://github.com/tao3k/poo-flow/actions/runs/36261908951/job/108459287469][POO Flow Ubuntu native gate]]
at 581.207 µs p95 under the unchanged 1 ms budget. This is one bounded
ten-edge chain shape, not a general update complexity result. The Rust oracle also records
that appending a blocking fact does not retract a previously derived negated
row, and that appending an aggregate source can retain the old total and
produce a new total different from a fresh program. These are observed
Rust 0.8.0 repeated-run behaviors, not a claim that nonmonotone updates have
clean incremental semantics. Scheme rejects such session updates.
The concurrent qualification launches four independent fixed-point programs
with Gerbil workers and checks every returned relation projection. It checks
reentrancy across programs; it does not establish intra-program parallel
execution or a throughput gain.
The grouped ternary two-hop fixture has two disjoint 50-edge chains. Its
second body atom binds both group and source node; the custom Provider
records the =(0 1)= composite key and returns the same 98 rows as Rust.
This establishes selected composite-key lookup behavior, not an SS scale
or allocation result for that plan.
The =ascent-byods-rels 0.8.0= macros for =eqrel=, =trrel= and =trrel_uf= have
binary and ternary declaration patterns.  A four-column grouped Rust oracle
probe fails macro expansion, so wider grouping is outside the pinned Rust
baseline.  The executable Scheme Provider remains restricted to the two
supported arities until the baseline is complete.
The string-keyed grouped BYODS query fixture joins each of =eqrel=, =trrel=
and =trrel_uf= to an ordinary =wanted= relation.  Empty, chain, and cycle
snapshots match the pinned Rust oracle.  This checks relation-body consumption
in addition to materialized output enumeration; it is not a storage merge or
scale receipt.
With two producer rules, the same fixture joins path segments across source
relations.  =trrel= and =trrel_uf= outputs match Rust 0.8.0.  For the grouped
=eqrel= case, the pinned Rust query omitted the =alpha= component after the
two-rule merge, while a single Rust producer over the identical union of
source facts and Scheme both returned it.  The differential test compares
=eqrel= to that single-producer baseline and records the split-producer
discrepancy separately.  It does not claim split-producer =eqrel= parity.
The minimized counterexample has only one group: =first(alpha, 1, 2)=,
=second(alpha, 2, 3)= and =wanted(alpha, 3)=. Pinned Rust omits
=matched(alpha, 1, 3)= with two producers but emits it when both edges enter
the first producer. Scheme emits it for either producer order and for the
combined input. In pinned =ascent-byods-rels 0.8.0=,
=eqrel_ternary.rs::merge_delta_to_total_new_to_delta= drains =delta.map=,
removes the matching group from =new.map=, merges their indexes, and does
not put that merged group back into =delta.map=. The following loop inserts
only groups still left in =new.map=. This explains the missing group at the
next delta read; it is specific to the ternary grouped provider path tested
here. Scheme retains equivalence closure semantics and does not copy the
missing Rust row.

The =eqrel= component index emits only newly joined cross-component pairs.
It avoids scanning all previously materialized pairs for every input edge.
The 20-edge source chain still produces all 441 expected facts, and the Rust
oracle now compares this complete closure plus reversed, duplicate,
reflexive and interleaved-group source snapshots. A concurrent qualification
case checks that separate evaluations do not share the component state. The
Rust split-producer discrepancy above remains.
The public storage =make-state= helper now creates provider state rather
than returning the method procedure. An evaluation calls this helper once
per relation. A Scheme qualification advances =eqrel=, =trrel= and
=trrel_uf= states across edge prefixes and verifies each extension returns
only rows absent from the prior materialization. This verifies the Provider
boundary but does not imply retained rule-program state.

The standard =ascent-byods-eqrel= SS scenario times 20 evaluations of a
predeclared 20-edge program per run. Before the component index, one local
run measured 3.508 ms p95. Three local runs after the change measured 450,
448 and 965 us p95, all below its 1 ms budget. These local samples do not
establish a cross-platform or large-scale performance bound.

The =trrel= and =trrel_uf= Providers now index emitted reachability pairs by
predecessor and successor per relation run. A new edge combines the already
known predecessors of its left endpoint and successors of its right endpoint;
it no longer searches the input-edge graph for each insertion. The Provider
preflights any batch whose upper bound exceeds the remaining fact budget
before committing a new pair to either index. Their 20-edge directed and reflexive closures
produce 210 and 231 facts and match the pinned Rust oracle. The Rust
differential also compares binary/grouped cycle and explicit-self snapshots;
four concurrent Scheme evaluations verify that Provider state is not shared.
An early combined =ascent-byods-trrel= SS case measured 2.493 ms p95 before
the index. The current scenario measures =trrel= and =trrel_uf= separately,
each on a 20-edge chain with a strict 1 ms admission ceiling. Local =trrel=
runs after the input-edge index ranged from 473 us to 3.748 ms p95; one
successful =trrel_uf= run measured 535 us p95. Several local runs failed the
1 ms gate. The combined baseline and separate-provider results are not a
direct speedup comparison, and stable submillisecond performance remains open.

The standard =ascent-rule-clauses= SS scenario measures evaluation of one
predeclared program over three ternary edges. A post-index isolated 20-sample
run measured 577 us p95; a post-Provider run measured 1.256 ms p95 with a
9.76 ms maximum, and two earlier post-lattice runs measured 1.689 and
1.515 ms p95. These long-tail samples occurred amid approximately 0.5 ms medians.
The 1 ms ceiling is not stable. The =ascent-indexed-joins= SS scenario uses 50
binary edges and measured 800 us p95 with the default index, and 663 and
851 us after adding the Provider seam. These are not cross-platform or
large-scale claims.
After adding storage Providers, one local 20-sample run measured 1.305 ms p95
for indexed joins and 1.804 ms p95 for the rule clauses; the latter exceeded
its 1 ms budget. The samples show that the new dispatch path needs further
optimization and that semantic parity alone does not close the performance
row.
After resolving the storage method once per relation, isolated local SS runs
measured 609 us p95 for rule clauses and 1.017 ms p95 for indexed joins, while
another indexed-join run exceeded 3 ms p95. These samples do not establish a
stable submillisecond gate.
After the =program/funs.ss= role split, two isolated local rule-clause runs
had approximately 0.58--0.59 ms medians but failed the 1 ms p95 gate at
1.803 and 1.706 ms. The functional split does not close the latency tail.
Declaration construction is outside this timing window and remains a separate
cost.

* Implementation order

1. Freeze a representative Rust 0.8.0 fixture corpus and error corpus for
   each matrix row; keep it under =rust/ascent-oracle/=.
2. Generalize relation columns and rule bindings in =program/=,
   retaining POO Core and standard-library operations as the substrate.
3. Implement and compare stratification, negation, generators, aggregation,
   and generic lattice behavior. Preserve explicit bounds and typed failures.
4. Add the BYODS provider boundary, repeated-run semantics, then serial and
   parallel execution parity.
5. Qualify Gerbil module and macro embedding plus performance against the
   corresponding Rust fixtures. Only then admit Agent-specific extensions as
   a separate research track.
