* Executable owner

=candidate/withdrawal-session.ss= admits one bounded positive candidate.
Initialization solves the copied source with the native evaluator and verifies
its complete grounded graph. Its POO owner then retains that graph, mutable
membership snapshots and private stable source occurrence tokens. Observation
and occurrence withdrawal are the only methods; no native engine or support
state escapes. Maintained rows follow surviving initial root order; the query
meaning is set-valued. Negative rules and reducers do not enter this positive owner.

#+begin_src scheme
(def owner (candidate-open-withdrawal-session snapshot proposal))
(candidate-withdrawal-session! owner 0 '((edge 1)))
;; => POO observation with source: (generation 1) and rows:
#+end_src

Requests supply the expected CURRENT generation. Public selectors are
=(relation one-based-position)= in that generation. Private tokens retain the
initial occurrence identity even when positions shift or row values coincide.
Unknown, duplicate, empty, stale and over-budget requests fail before publication.
An equal candidate-owned fact is a separate support and survives source removal.
This is local cut consistency, not authority to retire an external source.

Each observation captures its source AND row roots at creation. POO field
laziness must not read a mutable current-state cell later. Source identity,
source pairs and row pairs are copied on observation. Holding an old observation
across another cut cannot change its generation, rows or source contents.

* Maintained positive transaction

1. Validate generation and every current occurrence; translate to stable tokens.
2. Copy the prospective source cut and filter its token lists in the same order.
3. Stage DRed overdelete/rederive against the initially verified complete graph.
4. Complete bounded work and allocate the prospective rows/source/support/token state.
5. Publish through one private state swap.

Positive source deletion cannot introduce a new grounded rule instance.
The initial graph covers all future subcuts; cumulative removed-token membership
retires initial source edges without changing the graph. Candidate constants and
remaining grounded alternatives can rederive overdeleted facts. Unsupported
cycles cannot seed themselves. No graph replay or native fixed-point solve runs
on subsequent cuts. The initial certificate remains bound to its initial cut;
it is not republished as a fresh certificate for later generations.

Failure preserves the previous cut, including token translation. The owner
serializes public method calls and rejects reentrant access. Callers must
serialize concurrent access; this is not a thread lock. Insertions require a
new owner and complete graph admission. Physical edge compaction is not added.

* General native transaction boundary

=gerbil-ascent-session-replace-sources!= retains its optional trusted
=result -> Boolean= acceptance procedure. Only exact =#t= accepts. It checks a
completed prospective result before native engine/source publication; reentrant

It continues to serve native affected-component replacement for general admitted

* Matched complete lifecycle costs

=t/performance/withdrawal-support/replay-reference.ss= freezes the =f1bd5ef=
per-cut graph-replay algorithm. Both arms receive the same held-observation bug
fix and share current native dependencies. This compares algorithms, not two
historical toolchain builds. The maintained arm uses the same initial native
solve and graph admission, then DRed; the baseline uses complete graph replay
and native Session replacement at every cut.

Both measured lifecycles include construction, all source deletions and public
observations. Fifty paired samples alternate order. After each sample, every
source generation and complete query row set is compared across arms and to an
independent source-pair BFS, outside measurement. Chain and diamond require
20 percent CPU reduction, 25 percent allocation reduction and 35/50 CPU wins.
Duplicate and tiny controls allow at most 10 percent plus 20us CPU and 10 percent
plus 4096 bytes allocation. Thresholds were fixed before measurement.

The first stable-token experiment retained native replacement at every cut.
It failed the chain contract (CPU 12.088 to 10.094ms; allocation 18,463,208 to
16,067,072 bytes). That rejection remains in the local receipt. Moving the
positive owner to maintained DRed is the subsequent algorithm change; neither
budgets nor admission thresholds were widened.

The subsequent native run passed all four scenarios. Chain median CPU was
12.206 to 8.346ms and allocated bytes 18,463,208 to 13,487,768; diamond was
11.324 to 7.858ms and 17,357,112 to 12,979,008 bytes. Both targets won all
50 CPU pairs. These are eight-cut finite lifecycles. Allocation is not a
resident-memory measurement: the initial complete graph stays resident until
the owner is released, even after all sources are withdrawn.

* Native gate isolation

The combined nine-Suite GxTest hit its unchanged 120-second deadline during
the older change-plan Suite, before the new support Suite ran. The gate now
uses =tools/test-performance-contracts.ss= with the declared ASP testing memory
and process-isolation profiles. Every child is the standard native GxTest with
2 GiB; each Suite runs in a fresh process. Existing Scheme workgroups and ASP's
native core-capacity projection dispatch independent Suites concurrently;
paired arms stay sequential and counterbalanced inside each process. CPU
counters are process-local. Separate logs preserve contiguous native Case
receipts, while actual completed work is forwarded during execution. The enclosing total deadline remains
120 seconds. Native child failure is explicitly propagated and was qualified
with an intentional failing Case. Source discovery and build scheduling remain
Gerbil-owned. The serial isolated lane also exhausted 120 seconds after eight completed
Suites. Both negative logs remain retained. No sample count, CPU/allocation
threshold, source corpus, heap or deadline was relaxed. No second test harness
or Bash process scheduler was added.

The final native gate completed all nine Suites within that unchanged deadline,
with nine =MODULE-OK= receipts and a successful Case audit. In this concurrent
run, chain lifecycle CPU was 10.339 to 5.776 ms and allocation 18,516,992 to
13,488,824 bytes; diamond CPU was 8.869 to 5.774 ms and allocation 17,367,352 to
12,978,512 bytes. Both controls passed their original gates. These are finite
paired process-CPU and allocated-byte results, not an end-to-end wall-time or
resident-memory claim. An intentional failing child propagated exit 70 through
the workgroup runner; its failure cannot produce =PERFORMANCE-CONTRACTS-OK=.
