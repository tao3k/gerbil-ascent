** Exact edit scope for the public witness relation

=MaskWitness= models the existing bounded =mask_witness= rule.
=mask_witness_changes_iff= proves that one row changes exactly when the
scope selects both endpoints, that scope's membership of the witness
vertex changes, and the two shortest segments through the vertex fit the
total hop limit. The same law covers insertion and withdrawal. Group
membership and final candidate selection are absent from this rule.
Use the final-pair frame only for =group_answer= and =answer_trace=.
A repair that restricts all witness work to final candidate pairs can
omit rows that the current Result exposes.

=witness_pairs_exact= proves the enumerator's membership against that
delta. For a changed key =(scope,z)=, join the selected incoming
shortest-distance bucket at =z= with the selected outgoing bucket at
=z= and keep exactly the pairs whose distances sum to at most K.
=witness_pair_checks= gives the exact number of bound checks for a
direct nested scan. The total across edited keys is the sum of the
products of the two bucket lengths. Charge building and retaining
the buckets, looking up both buckets for each edited key, repairing
rows, and publishing provenance separately. Sparse edits can still
touch a dense bucket; edit count alone cannot set a crossover.

=repaired_mask_witness_eq_recompute= checks the complete edit
procedure at the level of row membership. Take a fixed admitted graph
cut and a complete inventory of changed =(scope,blocked-vertex)= keys.
For each changed key, join the incoming and outgoing shortest-distance
buckets. For each qualifying pair, insert the row if the new mask
blocks the vertex and withdraw it otherwise. Keep the old membership
for every other row. Lean proves that this produces exactly the
membership obtained by complete recomputation, for any edit with those
premises. The proof includes scopes outside required groups and pairs
outside the final candidate set.

** Distance-ordered witness search

For one edited key let =I= and =O= count the incoming and outgoing
entries, and let =R= count accepted pairs. The direct join checks
=I*O= sums. If an outgoing index enumerates entries in nondecreasing
distance, a scan for one incoming entry can stop at the first sum
above the hop bound. =witness_prefix_exact= proves it selects exactly
the same entries as filtering that index. =witness_prefix_checks=
counts each accepted entry and one failed comparison if a rejected
suffix exists. =witness_prefix_join_checks= bounds total comparisons
by =R+I=. =sparse_prefix_checks_save= establishes a strict reduction
if =R+I < I*O=. When all sums fit, =dense_prefix_checks_equal=
proves that the two methods perform the same number of comparisons.
An edit may touch one key and still have this dense shape.

The existing =mask_witness= rule reads the two shortest-distance
atoms and then tests the hop bound. Its actual join orientation and
candidate count must come from native counters. The equation =I*O=
describes the explicit nested comparison baseline. The current native
comparison count and elapsed cost require separate evidence.

*** Exact cost test for this candidate

Let =F= count incoming occurrences for which the outgoing bucket has
at least one distance beyond the bound. In an index that is a
distance-ordered permutation of the original occurrences,
=witness_prefix_join_checks_exact= proves that the scan makes exactly
=R+F= guard checks. Count occurrences in both =R= and =F=. This also
covers empty buckets and multiple entries with the same distance.

=witness_prefix_budget_iff= gives the strict crossover for one bucket
when equivalent guard checks have a common cost =c= in the chosen
additive work unit. The extra cost of the prefix route must satisfy
=extra < c * (I*O - (R+F))=. Equality breaks even. The dense case
leaves zero guard savings. =equal_bucket_sizes_do_not_select_prefix=
uses the same hop limit and two incoming and two outgoing entries in
both examples. The dense case needs four checks and the sparse case
needs two. The sparse case gains with one extra guard-equivalent unit
and breaks even with two. A threshold on bucket length alone would
give both cases the same decision.

Map =I= and =O= to the two =mask_shortest= probes in the actual
=mask_witness= join after endpoint selection. Map =R= to the input
occurrences passing its hop guard, before publication deduplication.
Match both probes to the same admitted cut and preserve occurrence
identity through the distance index. Charge index construction and
invalidation once per applicable cut and charge order restoration,
publication, and evidence on each request that performs them. A trace
of a different join orientation uses that join's measured counts.
The theorem prices modeled guard work. Whole-request wall time,
allocation, and retained memory each require their own ledger.

** Search algorithm and its application boundary

For selected endpoint requests, one forward bounded breadth-first search
per distinct start and one bounded search over incoming edges per distinct
target are sufficient to decide the total-hop witness predicate. The
frontier contains exactly the vertices first reached at its distance.
The reverse-distance theorem preserves the directed suffix from a blocked
vertex to the target. Record all shortest last edges when retaining
predecessor evidence. A single parent can reconstruct a path. The
published =mask_predecessor= relation includes every qualifying last edge.

Let S and T count distinct search roots across a fixed graph cut and
let M count stored directed adjacency entries in either orientation.
Under the once-per-root premise, expansion examines at most
=(S+T)*M= entries. For a complete directed graph with self edges and
K >= 1, an all-source forward join examines M entries from the
identity layer and N*M from each of the K-1 additional input
layers, where N counts vertices. The modeled strict expansion saving
holds if S+T < 1+(K-1)*N and M > 0. This comparison concerns the
specified forward join orientation. Native join order and counters
must establish the baseline visit count. It leaves adjacency build,
visited storage, mask joins, provenance, publication, selected reads
and allocation/GC to the measured end-to-end comparison.

The output bound applies independently of the expansion strategy. For
80 vertices and K=4, the complete hop relation alone requires 25,680
rows, even when the caller supplies one candidate pair. In the standard
constructor, the hop relation starts empty, and
[[file:../../../program/evaluate.ss::ASCENT derived fact budget exceeded][candidate publication]]
charges new facts against the configured derived and output limits. A
complete result for that graph would exceed both default limits (10,000
derived facts and 20,000 output facts) before counting the other relations.
Record the refusal in the dense control. For any timed dense case,
record the actual constructor limits and all completed output rows.
Lean counts necessary tuples. Wall time, allocation and collection
still require measurement.

the graph-derived relations across mask-only edits and improving
