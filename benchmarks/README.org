#+TITLE: ASCENT benchmarks

* Performance questions and measurement units

High performance must be demonstrated on the operation being claimed. Keep
these layers distinct when selecting an optimization and reporting a result:

| Layer | Existing native measurement | What a completion means | Remaining evidence |
|-------+-----------------------------+-------------------------+--------------------|
| Mailbox | =actor-mailbox-test.ss= ordered burst | Receiver checked one message | Does not execute a Session request |
| Session protocol | Same Suite, timed and throughput-only windows | Public state reply checked; caller mailbox preserved | A throughput-only window supplies no latency distribution |
| Resident evaluation | =actor-session-test.ss= phase Suites | Versioned result and complete expected tuples checked | Kernel work must be separated from materialization and caller checks |
| Index/provider | =provider-index-test.ss= physical callback intervals | Expected IDs checked; published snapshots remain isolated | Inclusive intervals overlap; do not add them as exclusive costs |
| Production transport | Rust =process_throughput= with actual runtime identity | Changed source replaced, result exported and independent oracle matched | Budget preflight, transport, evaluation and export are separate costs |

Use verified completions per second, complete request P50/P95/P99/maximum,
input/output cardinalities, CPU, GC and process resources. Report queue time
only where it is instrumented; do not infer it from total wall time minus CPU.
An unavailable or backward allocation counter is unavailable evidence, not
zero allocation. Cold preparation and caller compilation are independent axes.
Million-message throughput does not establish million-query throughput.
Existing semantic and performance gates remain required. The million-request
and sub-100-ms large-query targets require production evidence; neither follows
from a model proof or the configuration checks.

* Recursive query at fixed output size

Run the native 10,000-row closure Suite directly:

#+begin_src sh
timeout --signal=KILL 90s gerbil -:max-heap=2G,debug=q test -v 5 \
  -r '^actor-ten-thousand-closure-test$' benchmarks/actor-million-test.ss
#+end_src

Two Cases alternate source cuts and check every output row in each of 1,000
complete requests. Both produce the same 10,000-row closure. Redundant edges
in the second Case make the input non-functional. A third Case appends one
redundant edge per request and checks both the growing source count and the
unchanged closure. The receipts separately report the source update,
evaluation and publication, detached export and oracle time.

The serial upstream Rust Ascent comparison uses the release benchmark target
=actor_closure=. It uses the same base, branch and sparse append datasets,
checks the source size and verifies all result rows without sorting.

#+begin_src sh
cargo bench --locked --manifest-path rust/Cargo.toml -p gerbil-ascent --bench actor_closure
#+end_src

The default Rust cases solve a fresh cut. The separate =--retained= control
appends to the native relation and invokes =run()= on the same program.
Native output is a detached vector of typed tuples. Gerbil output is a
detached Scheme list of pairs. Count and value checks match across both;
the CPU cost of these output representations is included in delivery.

* Concurrent native requesters

Record the VM count, active VM processor count, evaluator worker count, and
calling Actor population separately. A single VM can interleave runnable
green threads while other Actors wait. These in-memory cases exercise
mailbox and Session-state contention. Asynchronous I/O needs a workload with
pending I/O and independent runnable Actors to measure that overlap.

The corresponding delivery probes are selected with
=actor-million-list-delivery-test=, =actor-million-visit-test=, or

The base query has 1,000,000 input facts and 1,000,000 complete exported rows.
The recursive query has 128 disjoint chains of width 128: 16,256 input facts
and 1,040,384 exported rows. Both plan 1,000 changed-source queries, alternating
two disjoint cuts. A bitmap oracle checks every tuple, duplicate freedom and
complete cardinality without asking ASCENT for an expected result. Refusal
controls cover missing rows, duplicates, foreign cuts and invalid paths.

The state Suite retains 1,000,000 source facts and independently checks
1,000,000 public state request/replies. A reply is a source generation and
=idle=, =running= or =draining=; it contains no query result rows. Its throughput
must never be labelled complete-query throughput.
The =actor-million-state-contention-test= selector divides the same one
million requests across a machine-sized set of concurrent Scheme callers
of the one Actor Session. Each caller checks its replies and records its
own latency samples. The caller count is a property of the workload.

Preparation, one cold complete query and changed-source requests are distinct
receipts. Complete query timing includes public Session execution and full row
export. Changed-source request latency additionally includes replacement and
independent oracle verification. Sustained throughput includes client checks
and progress reporting; reciprocal phase times are not throughput. The
existing strict 100 ms P95 policy applies only to complete populations.

The cold-query phase receipt measures Session run through publication, the
result accessor, and the independent oracle on the same request. Progress
receipts accumulate those phases and source replacement for completed
requests only. Wall time also includes loop and progress reporting overhead.
These receipts preserve where the workload spent time if the supervisor
expires before the planned population completes.

The query receipts bracket the run with Gambit's process counters. They
report CPU, GC CPU and natural collections for the same set of completed
requests, including the resident evaluator's green threads in that VM.
Preparation, result access and the oracle sit outside the CPU bracket, and
GC CPU is included in run CPU. The run bracket makes no claim about
cumulative allocation when the upstream counter moves backwards.

Workload-specific declaration ceilings admit the named data cardinalities.
The existing output budget counts source and derived facts: these new profiles
declare total ceilings of 2,000,000 and 1,056,640, respectively. The reported
complete query still exports only the named result relation;
production default ceilings and all older gates stay unchanged. Keep 2 GiB and
90 seconds for each Suite, without prewarming or retries. A timeout before the
planned population completes is a failed workload, not a throughput or P95
pass. Keep partial phase receipts and report the last completed operation.
Observe whole-process CPU and peak RSS externally. Raw Gambit allocation
counter deltas remain evidence; allocation is unavailable across collections
until the upstream counter is qualified. No patched runtime is required.

* Matched recursive production transport

The existing Rust =process_throughput= benchmark retains its complete row oracle
and changing source values. Set =ASCENT_BENCH_DSL=ascent= to load the original
closure DSL through =Engine.load_sources= and require an Actor receipt from
every Scheme query. The default =typed= fixture retains its ordinary Session
and requires that receipt instead. Rayon uses the same selected source after
owned projection. A receipt mismatch fails, including stale compiled carriers.

Set =ASCENT_BENCH_CLIENTS=1= for an isolated requester or specify the population
for a matched saturation experiment. Omission uses the machine's available
parallelism. This does not impose an Actor protocol capacity. The matrix tool
also defaults to available CPUs for callers and Rust threads, and compares
one, up to three, and machine-capacity VMs. Every VM has one processor. Rayon
thread-count controls fit the same machine. Use =--clients= and =--dsl typed=
only for explicitly labelled requester and ordinary-Session controls. Historical
33-row receipts used twelve callers and remain historical data; they do not
define the current default. The new matrix schema records actual CPU capacity,
requester population and DSL. Results from different schemas or caller modes
must not be pooled as one performance comparison.
The installed Python =ProcessPool()= and macOS =InstancePool()= also derive
their default owner population from Rust's =available_parallelism=. An explicit
=owners=N= remains a caller choice; neither constructor imposes a twelve-VM
default. Each owner retains one VM processor. Installed-wheel qualification
omits =owners= by default so it checks the public constructor itself.
The Python package reexports the Rust/PyO3 extension. Python qualification
scripts supply workloads and assertions; execution and runtime control remain
in the selected Rust or Scheme backend.
The Scheme wheel's process owner currently uses =python -c= to enter the Rust
worker export in its child process. This is interpreter-based bootstrap, not
a Python evaluator or scheduler. The default Rust-runtime wheel does not use
that Scheme process bootstrap. Do not describe both configurations as an
independent Rust executable.
Each matrix row now requires at least 1000 fixed-work request samples across
five windows, followed by its separate 30-second saturation window. Every
configuration within a workload executes the same total work. Keep the
original 240-second process limit and retain any timeout as a failure.

The grouped recursive case uses 256 chains of width 16, 3,840 input edges,
30,720 exported rows and at least 1,000 verified changed-source requests.
Keep finite resource prechecks when comparing the Rust interface. They include
an independent Rust budget execution before the native query and replacement;
the resulting measurements are not pure Scheme kernel timings. Keep encoding,
native calls, decoding/release, queueing and client oracle costs separate.

The Rayon fixture must execute and release its initial admitted result before
the first source replacement. This initialization belongs to startup, not the
measured changing-source requests. It uses the existing =SourceSession= lifecycle.

The measured client phases currently include the following production work:

| Client phase | Source | Included work |
|--------------+--------+---------------|
| =replace_ns= | =RuleSession.replace= and =admit_replacement= | Input construction, finite projection, Rust budget evaluation, payload conversion, native source replacement and acknowledgement |
| =run_export_ns= | =RuleSession.run= and result ownership operations | Finite projection, Rust budget evaluation, native run/export, row decoding, result authority check and release |
| Remaining request time | Benchmark =execute= | Sorting, independent complete tuple comparison and digest updates |

For Actor sessions the native replacement eagerly evaluates and publishes its
candidate; a following =source-run= may reuse that completed result. Therefore
=replace_ns= is not an enqueue measurement. Opt-in =ASCENT-VM-PHASE= and
=ASCENT-RPC-PHASE= brackets separate native encoding, calls, decoding/release,
GC and owner queueing. Time outside these native brackets remains unattributed
host work until directly instrumented; do not label it all as Rust inference.
Traced runs are diagnostics, separate from performance admission.

Potential projection or index reuse must be bound to the owner, immutable
source cut and current generation, with failure invalidation and fresh
cancellation/resource/publication checks. A public object's identity or a
previous successful validation is insufficient. In particular, controlled
execution currently disables retained scalar source indexes in =evaluate.ss=;
enabling them requires validating interrupted index construction and source
replacement, not just deleting that guard.

* Rejected reply-channel candidate (historical experiment)

The original implementation creates a private reply Actor for each synchronous
Session request, preserving the caller's mailbox. A candidate replaced that
Actor with a one-reply =std/sync/channel= channel, leaving owner-only state
mutation and generation/publication logic intact.

A declared 10000-pair alternating source-entry comparison checked identical
responses and caller-mailbox isolation. Both arms had P50 3 us and P95 4 us.
The accumulated individual request times were 120.487 ms for reply Actors and
170.859 ms for reply channels. The maxima were 33.148 ms and 46.802 ms. No GC
occurred in the paired loop. The study kept the existing reply Actor. These are historical measurements
from the isolated experiment. The native Suite above measures the installed
current Session on the same request shape.

* Retained Session publication

#+begin_src sh
timeout --signal=KILL 90s gerbil -:max-heap=2G,debug=q test -v 5 \
  benchmarks/session-publication-test.ss
#+end_src

Run the same checked DSL at 4096 and 16384 archive rows. The archive has
both source and derived rows. An independent replacement exercises completed
closure reuse for the archive, while an append and a replacement update the
small output relation. Record Session construction, first run, 1000 warm
public calls, append staging, append solving, replacement, and the first and
warm full exports. Hold earlier publications through both updates and check
every archive row in its original order. No full archive export is demanded
from the public result before measuring replacement.

The replacement interval includes re-admission, seeding the archived rows,
evaluation of the changed component and publication. The archived rows'
derived-budget charge uses the current source membership in
=program/reuse.ss=. Keep the number of hash operations separate from bucket
comparison and allocation costs. =SourceUpdateFrame.lean= relates ordered
first occurrences, source membership and the two budget checks.

The counter delta is reported only across monotone windows without a natural
