* Source and question

Arash Sahebolamri, Langston Barrett, Scott Moore, and Kristopher Micinski,
[[https://kmicinski.com/assets/byods.pdf][Bring Your Own Data Structures to Datalog]], OOPSLA2 2023, Article 264.
The question for this repository is precise: when a storage Provider
implicitly adds facts, can every rule consumer observe those facts at
the right semi-naive frontier, with the same result as the provider's
declared concrete relation? This paper is a core semantic reference for
=table/=, not merely a suggestion to use faster containers.

* Paper premises

| Locator | Result | Consequence for a provider |
|---------+--------+----------------------------|
| §3, PDF pp. 5–6, Theorem 3.1 | A monotone concretization makes the immediate-consequence operator monotone; =eqrel= is a positive example, while arbitrary lattice relations do not receive a blanket guarantee. | Specify the exact rows represented by private state; a successful insertion must not retract visible rows under the positive contract. |
| §3.3, PDF pp. 7–9, Theorem 3.5 | Semi-naive and naive DLDS semantics agree under the paper's total/delta concretization conditions. A newly implied =eqrel= pair must pass through delta; reading only the old total and a raw input delta can miss a later join. | Test the *emitted* frontier as well as the final closure, especially when two producer rules meet in one component. |
| §4, PDF p. 11 | All logical indexes must agree on concretization; key lookup and ReadAll expose the represented tuples. Concurrent traits and new/delta/total merge carry separate operational contracts. | Derive completeness from actual index construction and history, validate complete unique ReadAll key enumeration, and connect native equality/encoding to the same logical relation. |
| §5.1–5.4, PDF pp. 13–15 | Specialized =eqrel=, =trrel= and =trrel_uf= address equivalence and transitive relations in real analyses, including Polonius. | Compare on relation-appropriate graph workloads and record both full outputs and provider cost. Published speedups do not transfer to Scheme. |

The paper's =eqrel= and =trrel= represent distinct relation meanings.
Equivalence closure is reflexive, symmetric and transitive over known
members; transitive reachability is directed. A physical index Provider
that only changes lookup has a different obligation from a storage
Provider that changes the fact set.

* Failed read recovery at the Scheme boundary (2026-10-06)

Section 4's =RelIndexRead= supplies the concretization used by rule consumers;
logical index aliases must continue to represent the same facts. The paper
does not specify recovery from effectful Scheme callbacks. Our implementation
therefore needs a separate cache validity rule: a failed custom read cannot
certify that its physical state still represents the committed source version.

Lookup dispatch and complete candidate admission now form one failure boundary.
A raised callback or rejected answer revokes only the selected physical entry's
version and rethrows the original failure. Aliases rebuild that entry on their
next read, while another all/delta lane keeps its own valid entry. Successful
reads keep ordinary reuse; no automatic retry or callback correction is added.
See the [[file:../../scheme-research-proof-audit.org][research audit]] and

Rebuilding requires a Provider that can build a valid index again. Shared
nested field stability, external effects and general storage rollback remain
separate premises; this is not a new DLDS theorem or a performance claim.

* Storage injection ownership in Scheme (2026-10-06)

Sections 3.1 and 3.3 separate injection into private representation from the
facts exposed by total/delta concretization. At our Scheme boundary an
extension receives admitted facts and returns newly visible facts. It must
not retain writable access to the evaluator's source or published row spines.
Two native counterexamples exposed that access: mutating a returned row
changed an already-published result; mutating a retained input row changed the
source declaration used for recovery.

The immutable relation schema now selects storage dispatch once. Native Set,
=eqrel=, =trrel= and =trrel_uf= receivers retain direct dispatch by privately
captured identity. Custom receivers receive owned all/pending/input row spines;
a proper returned batch passes bounded arity admission before its spines are
detached. Initialization, rule emission and retained append share this seam.
Nested field identity remains shared, and all/pending header identity is
preserved when the engine supplied the same root.

The [[file:../../scheme-research-proof-audit.org][audit]] and
[[file:../../evidence/scheme-storage-spines-20261006/receipt.json][receipt]] bind native ownership and malformed-packet controls. This does not
prove arbitrary concretization completeness or roll back private Provider
state after a failed extension. Custom copies add work proportional to the
supplied snapshots and returned batch; no speedup is claimed.

* Custom state readiness and source replay (2026-10-06)

The injection/concretization transfer also needs a state publication boundary.
An extension can mutate private state and then fail, or pass its own shape
check before a later field, budget or rule callback rejects the evaluation.
A physical state that already remembers an unpublished fact can suppress it
on retry. The paper's Section 3 operators do not specify recovery from these
Scheme exceptions.

Custom engine states now have a private readiness owner. Dispatch marks them
pending; callback/shape failure marks them failed. Only complete source batch
or rule-round publication restores readiness. Pending states accept further
injections within the same round, but a later public engine run/append requires
all owners ready. Session recovery reconstructs fresh states from its retained
source snapshot. The shared schema caches dispatch only, never these owners.

The [[file:../../evidence/scheme-storage-state-20261006/receipt.json][native receipt]] covers mutable callback failures, shape/field/budget
rejection, a later guard failure after a successful emission, source replay,
and prior-result preservation. Native providers keep their raw state and
existing preflight laws. This prevents silent reuse of uncertain custom state;
it does not clone or roll back arbitrary private representation or undo host
side effects. Fresh independent state construction remains a Provider premise.

* Native kernel atomicity versus engine publication (2026-10-06)

Section 3.3's total/delta conditions apply to the facts actually consumed by
the evaluator. A native graph kernel can successfully inject an edge before a
stored-field checker or later guard rejects the enclosing evaluation. Its
standalone budget preflight does not undo that successful injection. Native
=eqrel= then remembers the edge and can suppress its entire four-fact frontier
on raw engine retry, even though the engine published none of those facts.

The schema now selects engine-specific storage dispatch. Native graph states
use the same readiness owner as custom states; their raw algorithms still get
borrowed rows and their original state values. Canonical Set remains direct.
The public raw algorithm dispatch and constructor retain the native protocol,
including standalone budget refusal/retry. Engine dispatch conservatively
requires source replay after a graph extension failure or interrupted round.
Session reconstructs fresh states through its existing recovery path.

The [[file:../../evidence/scheme-native-storage-state-20261006/receipt.json][native receipt]] binds the zero-frontier counterexample, stored-field
rejection and later-guard controls for all three native graph Providers,
Session recovery and raw algorithm regression. This extends the concrete
publication protocol; it does not prove arbitrary callback purity, private
state rollback or full native refinement. Added readiness work has no measured
performance benefit attributed to it.


* Completed closure reuse has a different state obligation (2026-10-06)

B23 §3.3, PDF pp. 7–9, relates each represented total/delta pair to its
concretization. It does not establish that copying enumerated closure rows
reconstructs an arbitrary Provider's private mutable state. In this Scheme
implementation, =gerbil-ascent-update-eligible?= admits exact Set storage or
registered stable lattice joins, exact hash indexes, and stable scalar values
and callbacks. =eqrel=, =trrel=, =trrel_uf= and custom storage stay outside that
completed-closure reuse admission; Session reconstructs them from source.
This is an implementation boundary inferred from the paper's premises, not
a claim that the paper proves the engine's failure recovery protocol.

=program/reuse.ss= now owns completed-row seeding as well as reuse capsule
admission. A private =closure-seed-state= groups prospective engine buffers.
The seed checks every retained row, counts unique derived rows against the
prospective source membership, enforces derived/output budgets, and seeds
both total and initial delta. Lattice membership uses final joined source
rows, so source joins do not consume the reused derived budget. The evaluator
keeps engine readiness and whole-round publication. No completed result or
cached analysis retains this mutable buffer frame.

This owner split repairs a concrete build gate: =program/evaluate.ss= reached
1006 effective lines and violated =GERBIL-SCHEME-MOD-R002= before tests could
run. The algorithm, row order, field callback behavior and budget checks are

* Physical index revocation and engine publication are separate (2026-10-07)

B23 §3.3, PDF pp. 7–9, requires represented total/delta facts to remain
consistent with the concretization; §4 adds indexes as implementation
structures. Those premises do not specify exception recovery for a mutable
index callback after engine admission. A cache's revoked version is therefore
insufficient evidence that the engine itself remains reusable.

The Scheme Set source flush admits membership before extending a live total
index. A custom extension that clears its index and raises can interrupt that
flush before total/delta rows, sizes and versions advance. The previous raw
engine accepted a second run, despite the interrupted membership publication.
The executable counterexample observes this successful retry; it is not a
performance result or a new algebraic proof.

The evaluator now owns an engine-local =publication-failed?= flag. Its shared
index advance dispatch marks this flag on any extension failure and rethrows
the original condition. Raw run, timed run and both source append entrypoints
require source replay thereafter. A successful whole-source replacement can
clear the flag because it builds and evaluates a fresh candidate before
adoption. Checked Session uses its existing reconstruction from the last
committed source cut. Private graph/custom storage readiness remains a
separate prerequisite and retains its original failure diagnostic.

This wrapper covers Set flush, whole-round commit and non-Set source admission
at their one index advance seam. A direct physical index owner can still revoke
and rebuild its cache from committed rows; the engine has the stronger burden
of preserving rows, membership, budgets and delta publication together.
Arbitrary callback effects and mutable nested fields remain outside this
recovery guarantee. The native Case checks ordinary and single-relation Set
entrypoints, Session restoration and old snapshot stability. See
[[file:../../evidence/scheme-engine-publication-20261007/receipt.json][the focused publication receipt]].


* Source reconstruction retires incremental state (2026-10-07)

B23 §3, PDF pp. 5–9, distinguishes injected source facts from a Provider's
concretized relation. Recovery has a corresponding Scheme ownership rule:
the new candidate is built from retained source logs, not from the interrupted
materialized relation or its counters. This rule is an implementation inference;
the paper does not prove the host's exception or Session publication protocol.

Two executable counterexamples extend the publication audit. First, a graph
injection mutates private state before a stored field rejects it. Raw source
replacement then completes in a fresh engine, but a later append still checks
the retired graph owner and is rejected. This occurs for =eqrel=, =trrel= and
=trrel_uf=. Second, a custom-storage append admits rows and increments the
source count before a physical index extension throws; its source log is not
yet updated. The old replacement preflight combines that tentative count with
the log length and rejects a legal 33-row replacement as though it had 34 rows.

=replace-source!= now constructs the complete prospective source cut first
and counts its rows, preserving duplicates as input facts. It publishes this
count and the fresh result only after successful evaluation. With
=recompute-from-source?= established by replacement, subsequent appends build
another fresh candidate and no longer inspect retired incremental owners.
Their old states are not marked ready or reused. Before successful replacement,
run and append remain subject to the storage and index publication guards.

The native Case checks all three graph providers against fresh evaluation,
then checks the 33-row input limit after an interrupted indexed admission,
a later replacement/append and stability of the original 32-row result.
The existing Session deletion matrix covers replacement budgets, retained
append logs, independent reuse, mutable callbacks and withdrawal. See
[[file:../../evidence/scheme-source-reconstruction-20261007/receipt.json][the source reconstruction receipt]]. This closes recovery handoff and budget
ownership; it makes no theorem, rollback or speedup claim.


* Eager recomputation must preserve Session snapshot ownership (2026-10-07)

B23's concretization maps private relation state to facts used by evaluation.
In a mutable host language, accepting or enumerating those facts also needs
an ownership boundary: external list mutation must not rewrite an admitted
source cut or the facts of a previously published result. This is a Scheme
implementation obligation inferred from the logical model, not a new theorem
about arbitrary host callbacks or mutable nested fields.

Two eager paths exposed an inconsistent boundary. Nonpositive source append
and raw source replacement evaluated a fresh non-retained engine, then stored
its result in a retained engine. That result's =rows-of= returned stored list
and row spines. Checked Session therefore published borrowed rows after eager
recomputation even though its ordinary retained result path detached reads.
The opaque single-source replacement path also retained the caller's source
list directly instead of copying its outer and row spines at acceptance.

The eager paths now evaluate through a fresh retained engine's =.run= so the
existing public snapshot routine detaches every list/row read. The opaque
Session replacement path owns the incoming source spines before passing them
to the engine and recording its pending source cut. Nested field objects keep
the existing shared identity and immutability premise. No deep copy, public
compatibility layer or alternate Provider protocol is introduced.

A native control forces these paths with negation and a derived hash Provider.
It mutates the returned input row and outer list after append/replacement,
mutates the caller's replacement row, and checks repeated reads, the previous
result and the next append's complete input/output against explicit scalar
facts. The timeout suite checks that eager validation still hands timed runs
to fresh committed round boundaries. See
[[file:../../evidence/scheme-eager-snapshot-20261007/receipt.json][the eager snapshot ownership receipt]].


* Source admission recovery follows the complete flush footprint (2026-10-07)

B23 §3.3 decomposes a database into total and delta states for semi-naïve
iteration; Theorem 3.5 relates the resulting semantics to naïve evaluation.
Its §5.5 separates logical index requirements from physical representations.
These logical conditions do not specify recovery from mutable host exceptions.
For our Scheme Session, an additional implementation obligation follows:
recover the accepted source cut when any physical owner in an append's flush
footprint fails. Invalidating the physical cache alone does not restore that
source cut.

A Set append normally buffers one row. Near the output budget it first flushes
all staged Set relations, including relations other than the append target.
The previous Session classification treated canonical Set storage as atomic
without considering its IndexProvider. A custom index extension could clear
its table and raise during that flush. The raw engine correctly quarantined
its failed publication, but the Session append fast path skipped recovery.
The next run consequently raised the replay error; its run-failure recovery
used the older committed cut rather than the accepted pre-append pending cut.

Session now computes whether every possible buffered Set owner uses a native
hash index provider. Set appends use guarded pending-source recovery whenever
that condition is false, including appends to a native-index relation which
can flush another relation's custom index. Lattice eager candidate evaluation
retains its existing atomic classification. Exact native Set/index programs
retain their direct path. The predicate is conservative about unused custom
indexes; it makes no performance claim.

The control starts with 32 source rows and one constant derived row, accepts
two distinct new rows, then triggers a flush at output limit 35.
A one-shot custom extension mutates and raises. Both append-target variants
must preserve 34 accepted source rows, both new rows, an empty unrelated
source, the constant output and the original
32-row public snapshot. The triggering row is excluded. This validates the
reconstruction boundary on scalar facts, not rollback of external callback
effects or a new theorem. See
[[file:../../evidence/scheme-append-flush-20261007/receipt.json][the append flush recovery receipt]].


An earlier development control used a duplicate buffered source. Its pending

* Concretized support and admitted row occurrences are distinct (2026-10-07)

B23 §3 models concretization into a powerset, with an idempotent join. Equal
facts therefore have one logical support element. Our Scheme source interface
also retains ordered initial rows, including duplicate occurrences and their
input-budget cost. A physical index receives that current row snapshot. A
custom receiver inherited from the native hash Provider must be able to return
its repeated rows just as the native index does. Treating the second occurrence
as an invented fact confused logical support with admitted enumeration.

[[https://www.cs.ucdavis.edu/~green/papers/pods07.pdf][Green, Karvounarakis and Tannen, Provenance Semirings (PODS 2007)]], §2–3,
provides a useful distinction: natural-number annotations express tuple
multiplicity, while the ordinary relation records support. We use that
counting idea only for a finite physical snapshot witness; our Datalog heads
still use existing Set admission. This change does not implement recursive bag
Datalog or provenance polynomial evaluation, nor extend B23's theorem to
mutable callbacks.

For each physical all/delta entry at version v, let M_v(r) be the number of
admitted occurrences of row r and K_v(k) the sum of M_v(r) over rows whose
projected key is k. For a returned candidate packet P, acceptance requires:

- complete row shape and membership in the represented snapshot;
- count_P(r) <= M_v(r) for every candidate, including overselected rows;
- sum of count_P(r) for requested-key rows = K_v(k).

Together these constraints require every matching occurrence and forbid extra
repetitions. Deduplicating either the Provider input or the returned packet
would change the source enumeration; merely allowing arbitrary duplicates
would permit unsupported rule invocations. The same cap protects other-key
rows in an overselected packet. Missing-key lookup may return no matching
occurrences while retaining bounded overselection, as before.

The private witness now retains row occurrences alongside represented keys
and per-key counts. Build captures all counts; incremental extension adds the
new admitted occurrences. Existing physical entry versions keep all and delta
independent and revoke failed lookups. No public type, compatibility wrapper,
source budget or native index representation changes.

The new low-level native control compares a duplicate-bearing custom hash
index with the canonical index, rejects one extra repeat and one omission,
checks recovery through an alias, extends all with a repeated row and confirms
delta remains unchanged. A Session control then repeats the previous flush
failure with an accepted duplicate source: pending reconstruction must retain
34 source occurrences, including two copies of (0 0), rather than falling back
to 32 committed rows. It covers both same-relation and cross-relation append
targets. See [[file:../../evidence/scheme-index-occurrences-20261007/receipt.json][the occurrence coverage receipt]]. This closes the duplicate replay
limitation recorded in the preceding slice for the qualified hash receiver;
fresh replay may still fail for other Provider/callback reasons.

The =384ab64= Provider-owned view proposal retains source duplicate counts and
unique derived admission. This explicit-row occurrence witness supplies the
first boundary's duplicate discriminator. A compressed relation view still
needs its own concretization, exact delta and logical cardinality; a custom
IndexProvider cannot obtain compressed semantics by omitting supplied rows.
The present repair does not implement or qualify that representation migration.
