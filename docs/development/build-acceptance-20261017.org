- 单次标准 BuildSpec 构建在固定 SHA 的原始 macOS Release 上通过；没有阶段拆分或上游补丁。
- 固定 Release 的完整测试库构建通过，production-rebuilt=0；全量语义／性能另行验收。
- Rust：92 项通过；严格 Clippy =-D warnings= 通过。
- 独立 Scheme 后端 API 编译检查通过。
- Lean：完整 AscentProof／AscentProofTests 构建通过，163 jobs。
- Quint：56 个模型、377 项正例／必需反例义务通过；conformance 输出与原 fixture 逐字相同。
- release PyO3 wheel 包含 196 个成员；独立接口矩阵绑定 288 份输入，35 组、199 项通过，原总预算 120 秒。
- Python IO：15 项通过；workbench：162 项通过。

前期 Homebrew 安装目录的 macOS 全量 Scheme 语义不列为通过：
原 180 秒总时限终止了该次运行，当时没有按 archive SHA 对齐原始发布包。
随后比对确认 =gxi=、=gsc=、=gxtest= 三个工具与发布包的 SHA256 均不相同；
相同 revision 不能替代相同构建产物身份，该次超时不用于判断原始 Release 有缺陷。
保留的原生采样显示子进程位于 =dyld → dlopen → mapSegments → fcntl=；
这只是启动阶段的观测，不能据此宣称已确认整个超时根因。
未增大时限，也未将已完成模块替代完整语料验收。

固定原始 macOS Release 的 12 进程全量运行同样在 180 秒终止，不能列为通过。
4 进程受控对照发现本地改名遗漏：一项测试仍导入旧的 =../native/artifact-admission=。
该引用已改为 =../harness/artifact-admission=；失败收据保留，最终结果以修正后提交验收。

首次从仓库根目录手动生成的 wheel 缺少源码身份资源，被原身份检查拒绝。
改用 CI 的 Python 项目目录、完整 features 和 release 命令后，真实 wheel 的身份与接口矩阵通过。
失败记录保留，不以手工补包或关闭身份校验通过。

* 现有 Release 的最小对照

两个程序共享一个含值与宏的模块；只调用标准 =defbuild-script=。
1 核和 4 核各使用独立源目录与 package prefix，各执行一次，不重试。
两个 binary 都必须 exit 0，并精确输出 =42\n=。

- macOS 原始 archive 经 SHA256 =0e18d063f888a73d9f9692d441fb3776898114e8440eada6876937d289578183= 校验：两个模式均通过。
- Linux 原始 archive 经 SHA256 =143c691fee5af4f9f631fd339f69a66f562e42e0bfc1d4ee2cda5fa8d35c35ee= 校验：两个模式均通过。
- 原生 Linux 对照源码 =581f2591e46ff53f43654ab99a6bd0917d4f0743=，
  完整日志／生成物／收据：https://github.com/tao3k/gerbil-ascent/actions/runs/38998285720 。

未拦截、延迟或替换编译器命令，也未注入失败。
这些对照没有复现此前推断的正常构建缺陷，不支持“必须修改上游才能简化”的结论。
有限案例不能证明所有并行形状正确；完整项目用现有 Release 单独验收。
由于宿主冷暖状态未配平，不能用这组时间推导并行收益。

此前上游 bootstrap 失败及新增故障恢复契约的失败保留在原运行记录中；
相关上游 CI 已停止，本次交付不依赖那些补丁，也未据此发布 SDK。
