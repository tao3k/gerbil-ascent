#+title: SDK compiler output reuse across executable build phases

* Scope

Reuse the existing released SDK, compiler executor and compiled Reader SHA-256
implementation. No SDK, upstream source, runtime, resource limit, cancellation,
provenance rule, semantic deadline or existing performance threshold changes.
Build-only helpers stay in bindings/build-entry.ss; the C ABI runtime does not
import this module. Unrelated feature edits are outside the commit.

* Actual duplicate work

The preceding build's 96 repeated static object compilations comprise 89
ASCENT objects and seven dependency objects. The SDK registers the ASCENT
runtime C producers, but closes their executor at each make boundary. The next
make therefore lacks those producer records and translates Scheme again.

Capture the SDK's actual producer predicate before the first make. After its
successful drain, observe only those registered outputs and their SHA-256
values. Register digest-validation jobs with the SDK in the next executor.
Its existing dependency barrier prevents link preparation until validation
succeeds, and propagates a changed or missing output as a build error. This is
scoped to one single-writer build invocation; it is not a persistent cache,
filesystem-existence shortcut, GSC wrapper or replacement scheduler.

The first executor is explicitly drained even when synchronous make or a warm
build submitted no jobs. Each executable still has a separate completed make
call, retaining isolation of shared C writers. Dependency files not registered
by the SDK remain on the original path; no producer evidence is invented.

* Validation and remaining scope

A cold diagnostic using the released SDK observes 126 admitted output paths.
Actual GSC invocations fall from 573 to 484, and invocations triggering C
compilation from 445 to 356. Repeated object paths fall from 96 to seven, all
in dependencies. The shared-host diagnostic wall time is not speedup evidence.

Two added artifact Cases use the real SDK executor: only registered outputs
cross a completed executor boundary; changed or missing bytes prevent the
dependent consumer from running. Every pre-existing semantic Case is retained.
The compiled artifact-test closure declares its build-only helper explicitly.

A separate hosted macOS 26 runner supplies uncontaminated timing controls.
The released binary requires macOS 26 or later; its SDK and declared dependency
seed are fixed for all controls. The predeclared order is baseline, candidate,
candidate, baseline. Each control starts with zero ASCENT artifacts, executes
the same policy-enabled build and test preparation, and rejects unrelated
compiler activity or production recompilation during preparation. Binary
receipts and common program source hashes are checked before retaining each
result. All controls are preserved; there is no fastest-run selection.

The complete macOS semantic and exact pushed-commit CI results, together with
the hosted control receipts, are recorded in PR #1 after execution. Compiler
output re-admission is not a new production source-refinement proof.

The Linux Release lacks the producer registry API; it admits no outputs and
retains its original build path. The same Cases check this fail-closed fallback.
The remaining seven dependency recompilations need a separate SDK producer
contract before they can be reused safely through this interface.

* Darwin CPU-counter units

A native calibration found an independent measurement defect in build
supervision: proc_pid_rusage CPU fields are Mach absolute ticks. Treating
them as nanoseconds underreports CPU time by 125/3 on this ARM host. A
one-second process-CPU workload produced approximately 24 million ticks;
mach_timebase_info converted that to 1.00005 seconds. The supervisor now
uses the host timebase for both self and reaped-child CPU. Positive advance
remains the activity criterion; no startup, idle, heap or acceptance deadline
changes. Linux accounting is unchanged. Raw ticks, rather than previously
mislabelled supervisor seconds, must be used for historical Darwin logs.
RUSAGE_CHILDREN CPU measurements and monotonic wall measurements in the
hosted controls already use seconds and are unaffected by this correction.
This unit error does not explain the historical 40.3% wall regression.

The diagnostic expander hook observed 265 distinct project source misses
and zero GSC jobs on an unchanged warm preparation. This identifies source
currentness/expansion work that remains even after fixing the missing-library
dependencies. These instrumented shared-host timings are not speedup evidence.
Native process disk-byte samples were partial; they do not establish an I/O
bottleneck or a unique cause for the historical first control.

* Admission workflow gap and executable cost policy

The earlier build-cost job did not check relative preparation regressions.
It checked experiment isolation, matching inputs and currentness, then printed
CONTROL-OK even for the historical 40.3% preparation increase. Reporting those
conditions as complete performance acceptance was incorrect. A subsequent
faster series cannot discharge that failure.

ExecutionPolicy.lean now defines the preparation-admission predicates over
unbounded natural-number observed costs. Theorems establish rejection of any
strict increase, rejection of unresolved failures, current/complete/accounted
admission, and preservation of a failure across arbitrary later observations.
The actual Python decisions and the Quint predicates are generated from that
same predicate AST. Formal CI regenerates and compares both files exactly.
PreparationAdmission explores the protocol with six required counterexamples:
dropped failure history, ignored regression, stale inputs, incomplete controls,
missing cost observations and ignored warm rebuilds. These are admission laws;
they neither predict wall time nor prove the host language/compiler correct.

The collector now emits native integer monotonic nanoseconds. The projector
uses both baseline and both candidate samples in the fixed ABBA order, compares
complete phase totals without floating-point ratios, and retains failures
across phases. It does not add a timing allowance. Existing runtime performance
thresholds, semantic deadlines and heap limits remain unchanged. Cost coverage
here means command wall/CPU receipts; it does not mean compiler, expander or
allocator source-work refinement has been proved.

The committed regression ledger retains Actions 39084120171 and 39088480174,
including the original source identities and both observations per arm. Legacy
seconds are floored to nanoseconds with less than one nanosecond error per
sample. Original raw controls remain authoritative. A later faster group does
not resolve either entry. Source-bound resolution certificates are not yet
implemented; arbitrary resolution flags are rejected. Accordingly, current
performance completion remains unqualified rather than being reported green.

A replay of the real 070cc8e/eddf4f9 ABBA receipts demonstrates the difference:
all three phase means were lower (build 19.2%, preparation 10.8%, warm 5.7%),
yet the new admission rejects completion while the historical failures remain
unresolved. The empty-history control admits those same observations. This is
a check of the real receipt projection, not a newly selected timing run or a
claim that the unchanged production code became faster.

Formal CI is independent of Rust/PyO3 execution. The independent Python
consumer checks retain their exact producer wheel and now run separately after
that producer. The aggregate gate still requires formal, Python consumers,
Scheme, Rust/PyO3 and all oracle shards. A Rust failure can no longer suppress
the Lean/Quint model checks.

Remaining gaps are explicit: complete compiler/expander/allocation work traces,
source refinement of receipt collection/decoding, verified regression-resolution
certificates, and the three-worker macOS runtime regression itself. No abstract
model or bounded model-check result closes those source obligations. The new
policy blocks unsupported completion claims while that work remains open.

* Source work diagnosis and bridge target removal

The original 39084120171 artifact is retained in full. Its prepare intervals
were 74.031/94.560 seconds for the baseline and 124.445/112.027 for the
candidate. Most of the difference is inside make: 69.976/89.458 versus
117.757/106.025 seconds. Source inventory alone does not explain it. That
receipt did not collect per-task CPU, allocation or faults. Its interleaved
human-readable compiler log is not a reliable exact invocation counter.
The historical failure remains unresolved; no later faster group clears it.

The initial bridge-target hypothesis is rejected for this preparation lane.
After removing interleaved supervisor messages, every original prepare log
contains the same 257 distinct compile-file jobs, with no differing job paths.
This reconstruction is not a complete process census, but it disproves the
claim that these logs show two extra bridge jobs. scheme-artifact-test is a
consumer of the separate compiled DSL lane; it is absent from the performance
consumers selected by prepare-test-library. Removing its declared dependency
does not reduce this lane's compiler jobs. The helper ownership move retains
identical bodies and passes all 18 artifact Cases, but is not a measured
preparation performance fix. The 40.3% failure remains open.

The actual dependency selector is now a Lean-rendered region in the existing
harness, with exact rendering checked by formal CI. The Lean model proves
that removing an inactive dependency leaves the selected sequence unchanged,
for arbitrary dependency/test lists. This prevents applying the conditional
two-phase removal theorem to an unselected declaration. It preserves the
previous order and flattening algorithm and introduces no extra module. The
Scheme compiler/library primitives and surrounding make/decoder are still
outside a complete source-refinement proof.

The work-only diagnostic uses disposable-prefix observers and the same
commands, SDK, ABBA order and process supervisor. It records every GSC
invocation separately with actual input hashes/bytes, exit, child CPU, RSS,
faults and block IO. The public expander import hook records ordered timing
and allocator snapshots for actual source/interface import requests, including
direct registry hits under the fixed SDK. These
snapshots are process-wide and inclusive, including observer overhead;
nested or concurrent imports must not be added as exclusive allocation.
Instrumentation timings never enter the ordinary latency admission. Malformed
traces fail decoding; absent import observers are explicitly marked unobserved.
Compiler failures keep their
original exit status; changed input bytes also fail the diagnostic compiler.

PreparationWork.lean checks additive compiler-job/input work, ordered
allocation subtraction, nested double-counting and the independence of wait
time from reduced work. Its removal theorem concerns two observed records, not two processes per
module or per logical compile-file job; those units must remain distinct.
PreparationWork.qnt checks observation coverage/currentness and six required
fault counterexamples. These checks do not prove the observer/decoder, SDK
expander, C compiler or allocator correct. Their source refinement and a
complete allocator/cost bound remain open. They are not used to certify a
wall-time improvement.

Workflow dispatch can select work-only mode and an explicit historical
candidate. Ordinary PR runs retain the original uninstrumented wall gate and
the independent three-worker/180-second source Suite. No timeout, heap,
performance threshold, cancellation or provenance behavior changes.
